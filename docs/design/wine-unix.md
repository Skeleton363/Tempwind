# Wine's Unix side with Emscripten (v3, Phase 2 M4)

Wine 11's ntdll Unix part, wineserver and win32u's Unix part, built with Emscripten as one wasm64 module that runs in the Windows process's Worker. This is the contract for M2's to M4's work packages and the base M5 builds on. The boundary to translated code is `abi.md` v5, "Wine boundary"; the address space is `guest-memory.md`; the Wine CI build, its published data and the packaging for this module are `wine-build.md`. The decisions behind it are in `docs/status/phase-2.md`, and the research in `docs/dev/research.md` (2026-11-06, 2026-11-13, 2026-11-14 and 2026-11-21).

- **v1 (M2)** booted to `LdrInitializeThunk`.
- **v2 (M3)** runs guest code to process exit. It adds:
  - syscalls, unix calls and contexts (section 11);
  - the run loop and translated code (section 12);
  - the rebased closure and the top-down ceiling (section 4);
  - invalidation and write-copy (section 6);
  - running, process exit, stdio as FIFOs, the lazy boot set and the install copies in `drive_c` (section 8).
- **v3 (M4)** runs console programs with threads. It adds:
  - green threads: create, start, exit, join, the parked main thread and the JS scheduler (section 9);
  - process exit from any thread, and host files (section 8);
  - signals delivered at the wait: SIGQUIT's kill and SIGUSR1's suspension (sections 7 and 9);
  - user APCs, suspension and another thread's context (section 11);
  - win32u's Unix side, its static unix library table and syscall table 1 (sections 2 and 11);
  - the session's shared memory as one memory (section 7);
  - what is deferred, and to when (section 13).

Line numbers refer to the pristine wine-11.0 tarball.

- **Patches** are diffs against the pristine tarball (`patch -p1`), applied in name order with no fuzz. Each starts with a header: what it changes and why, and the section of this file it implements.
- **The number range names the owner:** `00xx` build and headers, `01xx` the virtual backend, `02xx` the server, `03xx` ntdll startup, `04xx` win32u (M4). A later patch may touch a file an earlier one touched; the later range's owner then owns that file from the merge of the earlier work package on.
  - **M4's patches:** `0107` (`virtual.c`'s unix library lookup, section 2) and `0203` (`server/mapping.c`'s session memory, section 7) are WP2's, with the `04xx` range. `0201`'s `send_thread_signal` hunk is edited in place by WP1 (SIGQUIT) and then WP4 (SIGUSR1); no other package edits `0201`.
- **`src/`:**
  - `boot.c`: the `boot` export and the startup glue (section 8);
  - `green.c`: blocking, sleeping, waking and signal delivery (section 9);
  - `green_pthread.c`: the pthread functions Wine calls, thread create, exit and join included (section 9);
  - `inproc.c`: the in-process server transport (section 7);
  - `run.c`: the run loop, `tw_run_loop` (section 12);
  - `signal_wasm64.c`: the machine layer that replaces `signal_x86_64.c`. In M2: the process and thread setup of section 8, and stubs that stop loudly for the rest (`NtCurrentTeb()` is `thread.c`'s, which reads `teb_key`). From M3 also the dispatchers and the context functions (section 11);
  - `stubs.c`: libc functions Emscripten lacks (section 2);
  - `unixlibs.c`: the static table of unix libraries, in place of `dlopen` (M4, section 2);
  - `version.c`: the version strings Wine's build would generate;
  - `virtual_wasm.c`: the memory backend under `virtual.c` (sections 5 and 6);
  - `library.js`: the `--js-library` that declares the imports of `abi.md` v5;
  - `tempwind_private.h`: what the `src/` files share (`tw_unsupported`, the imports, the green thread and queue, `grow_to`, `tw_run_loop`).
- **Shared lists:** `library.js`, `imports.txt` and `tempwind_private.h` are shared by every work package, and so are `config.h`, `stubs.c` and the rename headers.
  - Each milestone's new imports and exports (`abi.md` v5, "Host entries of the Unix side") are declared in all three before its work packages start.
  - A work package that needs one more import appends it at the end of the list in its own commit. It never reorders or rewrites other lines, so the merges stay mechanical.
- **`rebase/`** is a self-contained crate, LGPL like the rest of `native/wine/`. It has its own PE reader and depends on no crate of ours.
- **Our patches and `native/wine/` stay public under the LGPL.** The JS host and the tests are our own code.

## 2. Build
`native/wine/build.sh [--out DIR] [--jobs N] [--census]` (default `DIR` = `target/wine-unix`). Everything it makes goes under `DIR`, so two builds with different `--out` don't collide.
1. **Source:** the tarball named under `"wine"` in `tests/targets/sources.json`, downloaded from its URL into `DIR/src/` (or reused there) and checked against the pinned sha256. It extracts only what it compiles: `dlls/ntdll/unix/`, the ntdll headers they include, `server/`, `include/`, and from M4 `dlls/win32u/`.
   - **The generated headers (M4):** win32u's sources include headers that Wine's build generates with `widl` from `include/*.idl`, and the tarball has only the `.idl`: `objidlbase.h` through `combaseapi.h` L29, which 24 of the 46 files reach, and `dxgi.h` and `d3d10.h` to `d3d12.h` in `d3dkmt.c` L34-37. They come from `tests/targets/wine.lock`'s native tree, built from the same tarball (`wine-build.md`), as `tests/wine/prepare.sh` unpacks it into `target/wine/native`: each `opt/wine-11.0/include/wine/windows/NAME.h` that the tarball's `include/` lacks and whose `include/NAME.idl` it has (340 in wine-11.0) is copied to `DIR/gen/include/`, which only win32u's include path has, after the tarball's `include/`. Without that tree, or with another tag's, the build fails, naming `prepare.sh`.
2. **Patches** from `native/wine/patches/`, in name order. A patch that doesn't apply cleanly fails the build.
   - **Then the syscall wrappers (M3):** `node native/wine/gen-syscalls.mjs` reads the patched tree's `dlls/ntdll/ntsyscalls.h` and `include/winternl.h` and writes `DIR/gen/syscall_table.c` (section 11). It is generated at every build and never committed.
   - **From M4 also table 1:** it reads `dlls/win32u/win32syscalls.h` with the prototypes of `include/ntuser.h` and `include/ntgdi.h`, into the same file (section 11).
3. **Compile** every C file through `scripts/emcc.sh`:
   - ntdll's Unix part: the `UNIX_SRCS` of `dlls/ntdll/Makefile.in`, except `signal_*.c`, which `src/signal_wasm64.c` replaces;
   - the server: the `SOURCES` of `server/Makefile.in`, with `-include rename-server.h`;
   - **win32u's Unix part (M4):** the `.c` entries of `dlls/win32u/Makefile.in`'s `SOURCES` whose file has `#pragma makedep unix`: 46 in wine-11.0 (`Makefile.in` L11-58, `dibdrv/` included), all but `main.c`, the PE side. With `-D_WIN32U_` (its `EXTRADEFS`, L1) and `-include rename-win32u.h`;
   - `src/*.c` and `DIR/gen/syscall_table.c`.

   The flags: `-m64 -O2 -sSHARED_MEMORY -fwasm-exceptions -sSUPPORT_LONGJMP=wasm -DWINE_UNIX_LIB -include native/wine/config.h`, the defines Wine's makefiles give each directory (`EXTRADEFS`), and Wine's include paths, with `native/wine/include` first. `-sSHARED_MEMORY` at compile time turns on atomics and bulk memory, which the shared-memory link requires of every object (wasm-ld refuses an object without them).
4. **Link** `DIR/wine-unix.mjs` and `DIR/wine-unix.wasm` with the spike's flags (`abi.md` v5, "Instances") and these:
   - `-sINITIAL_MEMORY=4GB` (section 5);
   - `-sSTACK_SIZE=1MB -sSTACK_OVERFLOW_CHECK=2`: with `GLOBAL_BASE` the layout is data, then the stack, then the heap, so the stack grows down into Wine's globals;
   - `-Wl,--wrap=sbrk` (section 5);
   - `-Wl,--fatal-warnings`;
   - `--no-entry`, and `-Wl,--error-limit=0`, so that one link reports every undefined symbol;
   - `-Wl,--no-gc-sections`: every compiled function stays in the module, so gate 1 covers all of Wine's code. With section GC, wasm-ld drops what the entries don't reach and doesn't report the undefined symbols of dead code; while `boot` and the server's entry are skeletons, that is nearly all of Wine (the first link: a 19 KB module).
   - `-sEXPORTED_RUNTIME_METHODS=FS,ENV`;
   - `-sEXPORTED_FUNCTIONS=` the host entries of `abi.md` v5;
   - `--js-library native/wine/src/library.js`.

   Each `native/wine/tests/NAME.c` links with the same objects into `DIR/test-NAME.mjs` and `.wasm`, with `tw_test_main` exported in place of `boot`.
5. **Gates.** Each failure names what to fix:
   1. **No undefined symbols.** The link keeps Emscripten's default `ERROR_ON_UNDEFINED_SYMBOLS=1`: no `-sERROR_ON_UNDEFINED_SYMBOLS=0`, no `--allow-undefined`, no `-sWARN_ON_UNDEFINED_SYMBOLS`.
   2. **Imports:** every import of every module built (module and field, read from its import section) is listed in `imports.txt`. A new import needs its line, with a reason, in the same change.
   3. **Collisions:** `emnm` over three parts, the server's objects, ntdll's (with `src/`) and from M4 win32u's, finds no global symbol defined by two of them that a rename header doesn't rename. `rename-server.h` renames the server's side of a collision and `rename-win32u.h` win32u's; ntdll keeps its names, since win32u calls ntdll's exports by name, as `win32u.so` does through `ntdll.so`. `--census` prints the lists, so the headers can be regenerated from them.
   4. **Syscalls (M3):** the generator's checks pass (section 11), for table 0 and from M4 table 1. It prints every entry it couldn't match and exits nonzero.
6. **`DIR/build-info.json`:** the emcc version, the tarball's sha256, each patch with its sha256, the import list, and the sizes of `wine-unix.wasm` raw and gzipped.

**`config.h`** is a non-Linux POSIX profile. Every `HAVE_` it defines is true of the 6.0.12 sysroot: the header exists and the function links. Anything Linux-only (`__linux__` branches, `prctl`, `epoll`, `inotify`, futexes) stays off.

**`stubs.c`:** a function Wine calls that the sysroot lacks gets a stub here. Each stub says why. It either fails with an errno that Wine's caller handles, or stops loudly with `tempwind: unsupported: <name>` on stderr and `abort()`. A stub never pretends to succeed.

**win32u's optional libraries (M4):** FreeType, fontconfig, Vulkan and EGL are optional in Wine through `SONAME_*` (`freetype.c` L74 and L1458, `vulkan.c` L3004, `opengl.c` L874). `config.h` defines none of them, so none is loaded; with no FreeType, `font_init` returns with no fonts (`font.c` L6742). Console programs draw no text.

**Unix libraries (M4, patch 0107, `src/unixlibs.c`):**
- **Wine's path:** a builtin DLL's `__wine_init_unix_call` asks for its funcs with `NtQueryVirtualMemory(MemoryWineUnixFuncs)` (`dlls/winecrt0/unix_lib.c` L92-96). That reaches `get_builtin_unix_funcs` (`unix/virtual.c` L837-863, whose only caller is L6113), which `dlopen`s the module's `unix_path` and `dlsym`s `__wine_unix_call_funcs`. `find_builtin_dll` records `unix_path` without checking that the file exists (`unix/loader.c` L1358-1363).
- **Ours:** `get_builtin_unix_funcs` calls `tw_unixlib_funcs(unix_path, wow)` in place of `dlopen` and `dlsym`, under the same `virtual_mutex`, and returns `STATUS_SUCCESS` with the funcs it gives. libc's `dlopen` stays unused: its `dlerror` reaches `__get_tp`, which stops loudly (`stubs.c` L36-43).
- **`tw_unixlib_funcs`** looks the path's file name up in a static table, `{ "win32u.so", __wine_unix_call_funcs, count }`, and returns the funcs. A `wow` request, or a name not in the table, stops loudly with `tempwind: unsupported: unix library <path>` (a `wow` request adds ` (wow64)` after the path). `tw_unixlib_count(funcs)` gives a table's count to the unix-call dispatcher (section 11), and 0 for a handle that isn't one of them. In 7zz's closure only ntdll and win32u have Unix sides, and ntdll's own table doesn't come this way (section 8).
- **win32u's table** is `__wine_unix_call_funcs` (`win32u/syscall.c` L108-111), one entry, `init`. Its count comes from the `04xx` patch, as `0301` gives ntdll's (`tw_unix_call_count`).

**In CI**, `.github/workflows/wine-unix.yml` runs `build.sh`, then `npm run test:wine`, and publishes `wine-unix-<sha7>` with `scripts/release-publish.sh`: `wine-unix.mjs`, `wine-unix.wasm`, the test modules and `build-info.json`. `tests/targets/wine-unix.lock` names the release that tests use when they don't build. In a session, `build.sh` runs through Docker (`docs/dev/commands.md`).

## 3. The guest is AMD64
- **The module is wasm64; the Windows it describes is x86-64.**
  - A `__x86_64__` branch that describes the **guest** gets `|| defined(__wasm64__)`: Windows structures, `CONTEXT`, the TEB and PEB layouts, the PE machine, `is_win64`, the syscall frame's layout.
  - A branch that describes the **host CPU** doesn't: inline assembly, signal contexts, `cpuid`, `xgetbv`, `fxsave`, `rdtsc`, the host page size. It gets a wasm64 path or a stub.
- **`_WIN64`:** `include/basetsd.h` defines it for `__wasm64__`, as for `__x86_64__`.
- **`C_ASSERT`s** in `src/version.c`: `sizeof(ULONG_PTR) == 8`, `sizeof(INT_PTR) == 8`, `sizeof(CONTEXT) == 0x4d0`, and the `CONTEXT` offsets the boot test reads.
- **CPU information comes from the translator's profile** (`abi.h`, section "CPUID"):
  - `system.c`'s `do_cpuid` reads `TW_CPUID_LEAVES`. Other leaves return zeros, as the translator's `cpuid` does.
  - `do_xgetbv` returns `TW_XCR0`. Wine never reaches it, since the profile has no OSXSAVE.
  - The `fxsave` DAZ probe reads `TW_MXCSR_MASK`, what the translator's `fxsave` stores (0xFFFF).
  - `NumberOfProcessors` and the active processor mask are 1.
- **Segment selectors:** `cs64_sel` = 0x33 and `ds64_sel` = 0x2b, the x86-64 user selectors; the thread's FS selector is 0 (no WoW64).

## 4. Address map and image placement
`guest-memory.md`, "Address map of one process", is the layout. What it means for Wine's code:
- **Wine allocates only in the guest regions.** The preloader's reserve list becomes a static list: [0x10000, 0x7ffe_0000), [0x7ffe_0000, 0x7fff_0000) for KUSER and the syscall slot, and [0x1_0000_0000, 0x4_0000_0000). The NULL region, the gap and the host region are outside it, and `NtQueryVirtualMemory` reports them as reserved. A query at or above 16 GiB, the working-set limit, returns `STATUS_INVALID_PARAMETER` from Wine's own check (`virtual.c` L5740).
- **Limits:** `address_space_limit`, `user_space_limit`, `working_set_limit` and `host_addr_space_limit` are 0x4_0000_0000 (`virtual.c` L191-199). 64-bit Wine never lowers `user_space_limit` for an EXE without `LARGE_ADDRESS_AWARE`, and neither do we. `address_space_start` starts at 0x110000, Wine's x86 value, which keeps the DOS area clear. `virtual_set_large_address_space` (L5022, called from `env.c` L1849) lowers it to 0x10000 for a 64-bit process, as in Wine. For an EXE with both `HIGH_ENTROPY_VA` and `DYNAMIC_BASE`, it also frees the low region's reservation.
- **Wine's own bookkeeping lives in the host heap:** the virtual heap (`alloc_virtual_heap`, L3600), `pages_vprot` and the view tree. None of it is in a guest region. `anon_mmap_alloc`, which allocates it (and `server.c`'s fd cache and `sync.c`'s cache), takes zeroed memory from the host heap.
- **The host region** [0x8000_0000, 0x1_0000_0000) belongs to the Unix side's allocator: Emscripten's static data from `GLOBAL_BASE`, the 1 MiB stack, then the heap up to 0x1_0000_0000. The runtime's data in it (state blocks, the lookup table, the page-state table) comes from the raw `malloc` export.
- **Images:**
  1. An image maps at its preferred base when [base, base + size) is free and inside a guest region. `map_image_view` tries the preferred base first for every image.
  2. Only if that fails does a DLL marked `ImageDynamicallyRelocated` ask the server (`get_image_map_address`, `virtual.c` L3403).
  3. Otherwise `map_view` searches top-down for relocated DLLs, as Wine does. For an image based above 4 GiB, the search runs first in [0x1_0000_0000, `TW_IMAGE_RANGE_END`), then in the whole guest regions. Wine's own first range ends at `limit_high`, 16 GiB, so a top-down search there would grow the memory to 16 GiB (found by M2's WP2).
  - **The server's ranges** (`server/mapping.c` `init_memory`, L271-276): `ranges64` is [0x1_0000_0000, `TW_IMAGE_RANGE_END`), assigned top-down, so the first slot ends just below the rebased closure and the memory stays small. `ranges32` stays [0x6000_0000, 0x7c00_0000).
  - **`TW_IMAGE_RANGE_END`** = 0x1_6000_0000 (`abi.h`, M3) is the one constant behind both: patches 0102 and 0201 and the `section` harness use it. In M2 both ended at 0x1_7000_0000.
  - **The rebased closure (M3):** packaging gives every closure DLL except ntdll, kernelbase, kernel32 and apisetschema a unique base in [`TW_IMAGE_RANGE_END`, 0x1_7000_0000) (`wine-build.md`, "Packaging").
    - So each maps at its preferred base, is not relocated and keeps its AOT module.
    - Without it, 60 closure DLLs share 0x1_8000_0000. All but the first to load would map at load-order-dependent slots, be relocated and miss their AOT modules.
    - 0x1_8000_0000 stays free for users' own DLLs: it is MSVC's default DLL base.
    - This differs from native Wine, which moves every `ImageDynamicallyRelocated` DLL into its ASLR range (`research.md`, 2026-11-13). Wine relocates a DLL only to the server's `map_addr` (`virtual.c` L3205-3223), and the PE loader relocates only a module that isn't at its `ImageBase` (`dlls/ntdll/loader.c` L2172-2173). So a rebased DLL at its new base runs unrelocated.
  - **The same files in the same load order land at the same addresses.** Nothing is randomized.
- **`MEM_TOP_DOWN` with no limit (M3, patch 0104):**
  - `map_view` searches a request with no `limit_high` from `min(user_space_limit, host_addr_space_limit)`, 16 GiB, down (`virtual.c` L2287-2295). A top-down allocation there would grow the memory to 16 GiB.
  - So a top-down `map_view` with no `limit_high` first searches below a ceiling: the end of the highest mapped image view, rounded up to 64 KiB. Only if nothing fits there does it search the full range, as Wine does. With no image view mapped there is no ceiling, and the search is Wine's.
  - Guest code reaches it through `NtAllocateVirtualMemory` with `MEM_TOP_DOWN` and no zero bits, which passes no limit (L5223-5228, `unix_private.h` L527).
  - Images never reach the ceiling: `map_image_view` always passes a `limit_high` (L3329). Neither does the Unix side's other top-down use, the PEB and TEB block below 2 GiB (L4054-4055).

## 5. Memory growth
- **One grower:** `virtual_wasm.c`'s `grow_to(end)` is the only `memory.grow` in the module. It grows the memory to cover `end`, rounded up to 64 KiB and never past 262144 pages, then calls the import `memory_grown`. A grow that fails makes the map fail with `ENOMEM`.
- **The heap never grows the memory.**
  - `INITIAL_MEMORY` is 4 GiB, so the memory covers the whole host region from the start.
  - `__wrap_sbrk` refuses any increment that would move the break past 0x1_0000_0000: it returns `(void *)-1` with `errno = ENOMEM`, and `malloc` returns NULL.
  - `emscripten_resize_heap` is therefore never reached. This settles the spike's first open item (`abi.md` v5).
- **The harness checks it:** after the backend has grown the memory past 4 GiB, a `malloc` that would cross 0x1_0000_0000 returns NULL, and the memory's size is unchanged.

## 6. The virtual backend
`virtual_wasm.c` replaces the host calls in `virtual.c`: `mmap`, `munmap`, `mprotect`, `madvise`, `msync` and the `anon_mmap_*` helpers. `01xx` routes them there.
- **Maps:**
  - a fixed map (`anon_mmap_fixed`) grows the memory to cover the range and zeroes it;
  - a try-fixed map (`anon_mmap_tryfixed`) does the same, but fails with `EEXIST` if any page of the range is already mapped;
  - a map at no fixed address takes a free range in the guest regions;
  - Wine's decommit is a fixed map, so a recommitted page reads zero;
  - `mprotect` is bookkeeping only. Wine keeps the protections itself, and nothing faults;
  - `munmap` marks the range free; the memory never shrinks;
  - the guest regions start mapped with no access, as the preloader's reservation would be: a try-fixed map there fails until Wine unmaps part of them, and `map_view`'s own map at no fixed address (not `anon_mmap_alloc`) finds only what Wine unmapped;
  - a map outside the guest regions fails: `EEXIST` for a try-fixed map, `ENOMEM` for a fixed one;
  - a fixed map zeroes only the pages that may hold nonzero bytes (mapped or `mprotect`ed accessible, or copied from a file), since grown memory is zero.

  The backend keeps its own record of mapped ranges, in the host heap.
- **File views are copies.**
  - A view copies the file's bytes into the range.
  - A writable **shared** view keeps the file (a `dup` of its fd), offset and size. It writes the bytes back on `NtFlushVirtualMemory` and on unmap.
  - A second writable shared view of a file range that already has one stops loudly (`tempwind: unsupported: second writable view`). Read-only and copy-on-write views can be copied any number of times.
  - Image sections are copies too.
  - The session's shared memory is not a view: win32u reads the server's own memory (M4, section 7, "Session shared memory"). A copy would go stale at the server's next write.
- **KUSER:**
  - `virtual_alloc_first_teb` commits the page at 0x7ffe0000, as in Wine;
  - `virtual_map_user_shared_data` maps nothing: the guest and the in-process server share that one page;
  - `virtual_init_user_shared_data` writes to 0x7ffe0000 directly, not through a second mapping.
- **The page-state table** (`abi.md`, "Page-state table"):
  - the backend allocates it (1 byte per 4 KiB page up to 16 GiB, 4 MiB, from the host heap) and exports its address as `tw_page_flags()`;
  - the backend keeps `PAGE_WATCH`: it is set on the pages of a write-watch view whenever Wine sets `VPROT_WRITEWATCH` there (commit, `NtResetWriteWatch`), and cleared whenever Wine clears it (a recorded write);
  - JS sets `PAGE_CODE` when it links a module, and clears it when invalidation leaves no module there (M3; `abi.md` v5, "Page-state table").
- **Pointer validation:** a bad guest pointer doesn't fault, so the three `__TRY` sites in `virtual.c` become checks against the views:
  - `virtual_check_buffer_for_read` (L4807): every page is committed and readable, not a guard page;
  - `virtual_check_buffer_for_write` (L4841): every page is committed and writable or write-copy;
  - `NtReadVirtualMemory` (L6693): the same read check on the source.
  - a write check that passes records the write on the write-watched pages it covers, as the fault it replaces would;
  - a buffer wholly in the host region passes: it is the Unix side's own memory, and Wine's Unix side calls these checks on its own buffers too.
- **Write-copy (M3):** a write to a write-copy page leaves it write-copy, whether it is a checked write in C or a store in translated code.
  - That is Wine 11's own behaviour. It has no `VPROT_WRITTEN`, and `virtual_handle_fault` changes only guard and write-watch pages (`virtual.c` L4538-4595). So `NtQueryVirtualMemory` reports `PAGE_WRITECOPY` before and after a write (`get_win32_prot`, L1866-1872).
  - M2's status note listed this as a difference from Wine. It isn't one.
- **Images (M3):** once an image view is mapped and relocated, the backend calls `tw_image_mapped(fd, base, size)` with the image file's fd (`abi.md` v5). JS links the image's AOT module before any of its code runs.
- **Invalidation (M3):** the backend calls `tw_invalidate(base, size)` before it unmaps or remaps pages that have `PAGE_CODE`:
  - an unmap or a free;
  - a fixed map over them: a decommit, a recommit, a view mapped over the range.

  JS removes every module whose code overlaps the range, so the next transfer there misses and translates the new contents. A range without `PAGE_CODE` needs no call. A store from translated code to a `PAGE_CODE` page is a store-check hit and stops loudly until Phase 4 (section 12).

## 7. The in-process server
The server is linked into the module and runs on the calling thread. `02xx` and `src/inproc.c`.
- **Wine's pipes and fd bookkeeping stay**, over Emscripten's pipes.
  - After `send_request` (`dlls/ntdll/unix/server.c` L183) writes a request, the client calls the server's `read_request` (`server/request.c` L328) for its own thread, synchronously: the server thread whose request pipe holds data. One request is pending at a time, since the client reads its reply before it sends another. The handler runs, and `send_reply` writes the reply to the pipe.
  - The client reads the reply as Wine does (`wait_reply`, L276).
- **Waits:**
  - a `wait_fd` read that gets `EAGAIN` blocks in `green_block` until the thread is woken;
  - `send_thread_wakeup` (`server/thread.c` L1196) also wakes the green thread.
- **fds:**
  - `wine_server_send_fd` sends nothing, since the client and the server share one fd table. `thread_get_inflight_fd` `dup()`s the client's fd by its number, since each side closes its own copy;
  - `send_client_fd` puts a `dup` of the fd on a queue, and `wine_server_receive_fd` takes it from there;
  - `create_process` gets the read end of a pipe for `msg_fd`; the client keeps the write end as `fd_socket`. Nothing is written to it.
- **Start:** `server_init_process` starts the server in place of `server_connect`, after KUSER is committed. It runs what the server's `main` would:
  - `create_server_dir`, which `open_master_socket` runs: the config directory's fd and the server directory, under MEMFS's `/tmp`;
  - `set_current_time`;
  - `init_memory`, with the page size 0x1000 and the ranges of section 4;
  - `init_directories(load_intl_file())`. `l_intl.nls` is found at `DATADIR "/wine/nls"` (`/wine/share/wine/nls`), `unicode.c`'s fallback, because `server_argv0` is NULL in-process and no other path is set;
  - `init_threading` and `init_registry`.

  Then it sets `server_start_time` as `main_loop` does, creates the process and its first thread as `master_socket_poll_event` does (`server/request.c` L543), and the client receives the request fd from the queue.
- **KUSER:** the server's `user_shared_data` pointer is 0x7ffe0000 (`server/mapping.c` L1502).
- **Not in-process:** the master socket, the lock file, daemonizing, signal handling and `main_loop`. Neither is `server_connect`'s `setup_config_dir` (`unix/server.c` L1322): nothing creates the prefix, its `drive_c` or its `dosdevices` links, or checks who owns it. The boot set brings the prefix (section 8). `initial_cwd`, the launch directory's fd that it returns, stays -1, so `server_init_process_done` skips its removable-media check. An fd event that only `main_loop` would deliver stops loudly: a partial reply write (`POLLOUT`), a read of `msg_fd` (`receive_fd`), and `main_loop` itself.
- **Signals to threads (M4)** (`send_thread_signal`, `server/ptrace.c` L254, patch 0201's hunk, edited in place): the signal goes to the target's green thread, which handles it at its next wait (section 9, "Signals"). It returns 1, as a `tkill` that reached a live thread does; for a thread whose green thread has ended it returns 0, as `tkill`'s `ESRCH` does. Any signal other than SIGQUIT and SIGUSR1 stops loudly. The callers in wine-11.0:
  - `kill_thread` (`server/thread.c` L1608-1631): SIGQUIT to a thread that is not in a server wait. A thread in one is woken with cookie 0 instead (L1617-1622), and its client calls `abort_thread` (`unix/server.c` L361). That includes a non-alertable `Sleep`, which sleeps in `select`, not in the server. `kill_thread` never targets the running thread: `terminate_thread` answers `self` for it (L1816-1817), and `terminate_process` skips the caller (`server/process.c` L1526, L944).
  - `stop_thread` (L955-961): SIGUSR1, for `suspend_thread` and the context requests (L2199-2230), once process init is done. A thread suspending itself sends it to itself.
  - `queue_apc` (L1450, L1467): SIGUSR1 for a system APC to a thread not in an APC wait. Inside one process the only system APC is `APC_ASYNC_IO` (`server/async.c` L264-284).
  - `propagate_console_signal_cb` (`server/console.c` L692): a console control event. Unreachable: no conhost runs (section 8).
- **Which green thread (M4):** the server names a thread's Unix thread by its `unix_tid`, which the client sends in `init_first_thread` and `init_thread` (`get_unix_tid`, `unix/server.c` L1527-1549, L1670, L1787) and the server records (`server/thread.c` L1758, L1796). `config.h` defines `HAVE_PTHREAD_GETTHREADID_NP`, and `green_pthread.c`'s `pthread_getthreadid_np` returns the green thread's id, so `unix_tid` is that id and `send_thread_signal` finds the green thread by it. Before its `init_thread` a thread's `unix_tid` is -1 (L404), and `send_thread_signal` returns 0, as Wine's does for -1 (`server/ptrace.c` L258-264). The other readers of `unix_tid` are Linux-, macOS-, `HAVE_LIBPROCSTAT`- or `HAVE_SCHED_SETAFFINITY`-only code that the build doesn't compile (`server/thread.c` L236-383, L793-806, L814-824; `unix/thread.c` L1905-1981), and `get_thread_from_tid` (`server/thread.c` L767-776), which only `sigchld_callback` (`server/ptrace.c` L173) and the hang-up below call.
- **A thread's end (M4):** a thread that ends closes its request pipe (`pthread_exit_wrapper`, `unix/thread.c` L1103-1111). Natively the server sees the hang-up in `main_loop` and kills the thread (`thread_poll_event`, `server/thread.c` L589-599: `kill_thread( thread, 0 )`), which signals the thread object, so a wait on the thread's handle ends, and removes it from its process. In-process nothing polls, and Emscripten's pipes report no hang-up, so `pthread_exit` (section 9) calls `inproc_thread_hangup(id)` (patch 0201, beside `send_thread_signal`), which does what `thread_poll_event` does for the server thread whose `unix_tid` is `id`, unless it has already been killed (a thread the server killed first: `terminate_thread`, `terminate_process`).
- **M2 and M3** sent SIGQUIT to `exit(0)` (one thread, so the process ended), and every other signal stopped loudly. M4's SIGQUIT ends only its thread, as `quit_handler`'s `abort_thread(0)` does (`unix/signal_x86_64.c` L2608-2614); that fixes M2's "every SIGQUIT exits 0".
- **Time:** `set_current_time` runs at every request and at every green switch.
- **Session shared memory (M4, patch 0203):**
  - **Wine's:** the server creates `\KernelObjects\__wine_session` (`server/directory.c` L501-502) and `mmap`s its file `MAP_SHARED` (`set_session_mapping`, `server/mapping.c` L1351-1373). It grows it by more `mmap`s of the same file (`grow_session_mapping`, L1375-1406, from `find_free_session_block`, L1408-1416); the growth rule is `max(old * 3 / 2, old + max(needed, 0x10000))` (L1382). win32u maps the section read-only (`map_shared_session_block`, `win32u/winstation.c` L106-144) and reads it under a seqlock (L82-92). Only win32u's Unix side reads it.
  - **Ours:** one contiguous reservation in the host heap, `TW_SESSION_CAP` = 16 MiB, taken by `set_session_mapping` in place of its `mmap`. The session blocks are ranges of it: the first at offset 0 with the mapping's size, and each grown block right after the previous one, zeroed as it is taken. `grow_file` still grows the section's file, so the mapping's size stays Wine's. Growth past the cap stops loudly with `tempwind: unsupported: session memory past <cap>`. A view asked for before `set_session_mapping` has taken the reservation stops loudly with `tempwind: unsupported: session memory: a view before the server set the session up`.
  - **The client's side** is section 2's `04xx` patch: `map_shared_session_block` takes `block->data = tw_session_view(off, &block->size)` instead of opening and mapping the section. `off` is Wine's offset rounded down to the 64 KiB granularity (L113), and the size runs to the reservation's end, as Wine's size 0 maps to the section's end (L127-128). So the block cache's strict `<` (L157) keeps finding later objects in the same block. A call before the server has set the reservation stops loudly.
  - **No guest view:** the guest never reads the session memory, so nothing maps it into a guest region. The server writes and win32u reads the same bytes, as with KUSER.
- **Kills:** a SIGQUIT kill ends the green thread through `abort_thread(0)` (section 9). `process_sigkill` runs only from the process-destroy path (`server/process.c` L623-650, L1003), which the in-process server doesn't reach: the process ends by `tw_process_exit` (section 8).
- **Registry saves** go to MEMFS as in Wine (on its timer and at exit). MEMFS is not persisted in M2.

## 8. Startup
`src/boot.c`, `src/signal_wasm64.c` and `03xx` (`loader.c`, `env.c`, `process.c`, `system.c`); the overlay's load is `02xx` (`server/registry.c`).
- **Entry:** `boot(argc, argv, flags)`, a raw export entered through `WebAssembly.promising` (`abi.md` v5). JS writes argv into the host heap through the raw `malloc`.
  - `argv[0]` is `/wine/bin/wine`, `argv[1]` the program as a DOS path (`C:\tempwind\hello.exe`), then its arguments.
  - `boot` records the launch directory, which is the cwd when it is entered. Its caller `chdir`s there first. In M3 the JS host `chdir`s to the program's directory in `drive_c`: `C:\tempwind` by default, or `opts.cwd`.
  - `boot` sets `WINELOADERNOEXEC=1`, as the wine loader's exec of itself does (`loader_exec`, `loader.c` L525), so `__wine_main` takes argv with no re-exec. Then it runs `__wine_main`.
  - `flags`: 0 runs the process to its exit (M3). `BOOT_STOP_AT_ENTRY` (1) stops at the entry, as in M2. Any other value, or a second `boot` in one instance, stops loudly.
  - **Return:** in run mode `boot` returns the process's exit status, the full Windows status, once the process ends itself ("Process exit" below). With `BOOT_STOP_AT_ENTRY` it returns 0 once it has stopped at the entry. A Wine error ends in `exit()` or `_exit()`, `abort_thread`'s included ("Process exit"), which the host sees as the rejection of `boot`'s promise with Emscripten's exit status.
- **The environment,** set by the JS host in `preRun` (libc builds `environ` from `ENV` during instantiation):
  - `WINEPREFIX=/home/runner/wine-prefix`, the path the prefix was made at (`wine-prefix.path`), since its `.reg` files hold it;
  - `HOME=/home/runner`, `USER=runner`, `LANG=en_US.UTF-8`, `TZ=UTC`;
  - `WINEDEBUG`, only when a caller puts it in the host's `opts.env`. Nothing reads the host process's own `WINEDEBUG`, and M2's tests set none.
- **Paths:** `init_paths` (`loader.c` L449) uses constant paths instead of `dladdr`: `/wine/lib/wine/x86_64-windows` for the PE files, `/wine/share/wine` for NLS and `wine.inf`, `/wine/bin` for the loader. `get_initial_directory` (`env.c` L1389) uses the launch directory `boot` recorded, not `getcwd()`, because the server moves the cwd.
- **stdio, as FIFOs (M3):** fds 0-2 are nodes the JS host makes with `mkdev` and then marks `S_IFIFO` through `node.mode`. I/O still goes to the device's callbacks by `rdev` (`research.md`, 2026-11-14), and writes reach the host synchronously. `isatty` is false.
  - **Windows sees pipes:**
    - `get_device_info` reports a FIFO as `FILE_DEVICE_NAMED_PIPE` (`unix/file.c` L7215-7218);
    - kernelbase's `GetFileType` maps that to `FILE_TYPE_PIPE` (`dlls/kernelbase/file.c` L3297-3309);
    - msvcrt marks the stream `WX_PIPE` (`dlls/msvcrt/file.c` L755-766).
  - **Why:** a native run whose output a pipe captures sees the same, buffering included. msvcrt gives a non-tty stdout a full buffer (`file.c` L866-880) and flushes it at exit (`dlls/msvcrt/main.c` L145). M4's `7z -so` needs a pipe too. M2's character devices made msvcrt treat stdout as a tty.
  - **No conhost:** with no tty, `get_initial_console` (`env.c` L1340) passes them to the server as plain handles (L1363-1370), and kernelbase starts no conhost.
- **The wineboot skip:** in place of `run_wineboot` (`env.c` L1537), boot creates `\KernelObjects\__wineboot_event`, runs `virtual_init_user_shared_data()`, writes wineboot's seven KUSER fields (NtBuildNumber, NtProductType, ProductTypeIsValid, NtMajorVersion, NtMinorVersion, SuiteMask, NtSystemRoot) as `create_user_shared_data` does (`programs/wineboot/wineboot.c` L319), then sets the event and waits on it as Wine does.
  - The values: the version `init_peb` gives the PEB (10.0, build 19045; `env.c` L1827-1834), `NtProductWinNt`, SuiteMask 0 and `C:\windows`. The PEB itself isn't set yet at that point (`init_peb` runs after `build_initial_params`), and native wineboot, which reads the version from the prefix's registry, writes these (`kuser.bin`).
  - **They stay in M3.** They are the prefix default, which native wineboot writes from its own `RtlGetVersion` (`programs/wineboot/wineboot.c` L342-350), never a program's. A per-program version (`AppDefaults\<exe>\Version`) changes only the PEB, through unmodified PE code (`version_init`, `dlls/ntdll/version.c` L473, called from `loader.c` L4452).
- **The overlay:** `native/wine/prefix/overlay.reg`, the per-boot keys wineboot would write. The JS host puts it at `/wine/share/tempwind/overlay.reg`; the server's `init_registry` loads it right after `user.reg`, with its keys relative to `\Registry` and as no save branch.
  - It holds the computer name (`TEMPWIND`, not the host's), the hardware description with the CPU from the profile (the values `create_hardware_registry_keys` derives from it: vendor, family, model and stepping, brand string, `FeatureSet`, one processor, ntdll's 1000 MHz), the processor variables of the system environment, and the volatile environment of the prefix's user.
  - Its keys name `ControlSet001`: the loader does not follow `CurrentControlSet`'s link.
- **No child processes:** `NtCreateUserProcess` returns `STATUS_NOT_SUPPORTED` and prints `tempwind: unsupported: NtCreateUserProcess <image>`.
- **The host-pointer slots in ntdll.dll (M3):**
  - `load_ntdll_functions` writes `TW_SYSCALL_DISPATCHER` into `__wine_syscall_dispatcher` and `TW_UNIX_CALL_DISPATCHER` into `__wine_unix_call_dispatcher` (patch 0301, edited in place).
  - `signal_wasm64.c` commits the page at 0x7ffe1000 and writes `TW_SYSCALL_DISPATCHER` there.
  - `__wine_unixlib_handle` gets the host address of `unix_call_funcs`, an opaque handle.
  - In M2 all three slots held a non-canonical poison value, 0xDEAD_0000_0000_0000, which M3 removed from the header. The addresses are lookup keys for the dispatchers (`abi.md` v5, "Syscalls and unix calls").
- **`BOOT_STOP_AT_ENTRY`:** `signal_start_thread` builds the start state as `init_syscall_frame` does (`signal_x86_64.c` L2896):
  - a `CONTEXT` at `((StackBase − 0x28) & ~15) − sizeof(CONTEXT)` with `ContextFlags = CONTEXT_FULL`, Rip = `RtlUserThreadStart`, Rcx = the entry, Rdx = the PEB, Rsp = StackBase − 0x28, SegCs 0x33, SegDs, SegEs, SegGs and SegSs 0x2b, SegFs 0, EFlags 0x200, the FPU control word 0x27f and MXCSR 0x1f80;
  - the main thread's state block: RIP = `LdrInitializeThunk`, RCX = the `CONTEXT`, RDX = the PEB, RSP = the `CONTEXT` − 8, the other GPRs 0, RFLAGS 0x200, the `TW_INIT_*` FP state (MXCSR 0x1f80, FCW 0x27f, FTW 0xffff; `abi.md` v5), GS base = the TEB;

  then it `longjmp`s back to `boot`, which returns 0. `tw_main_state()` gives the state block's address.
- **Run mode (M3):** `signal_start_thread` builds the same state and calls `tw_run_loop` on it (section 12) instead of stopping.
  - `LdrInitializeThunk` runs translated. Wine's PE `signal_start_thread` then calls `NtContinue(context, TRUE)` (`dlls/ntdll/signal_x86_64.c` L1018-1044), which switches to the `CONTEXT`: `RtlUserThreadStart`, and from there the program.
  - The loop ends only through process exit.
- **Process exit (M3, patch 0302):**
  - **The hook:** `tw_process_exit(status)` gets the full Windows status, before `get_unix_exit_code` (`unix/thread.c` L89-94) cuts it. Two places call it:
    - `exit_process`, first (`unix/thread.c` L1520-1524). It is `NtTerminateProcess`'s end for the current process once `RtlExitUserProcess`'s first call has set `process_exiting` (`unix/process.c` L980-981), and `exit_thread`'s for the last thread (`thread.c` L1501).
    - `NtTerminateProcess`, before its own `abort_process` call (`unix/process.c` L982): a process that ends itself without that first call, as `TerminateProcess(GetCurrentProcess(), status)` does.
  - **`abort_process` keeps its `_exit`** (`thread.c` L1485-1488). Its other caller is `abort_thread` for the last thread (L1477), Wine's end for errors:
    - a server protocol error (`unix/server.c` L163, L174);
    - a lost server pipe (L238, L267, L977, L1032);
    - a thread the server killed (L361);
    - SIGQUIT (`quit_handler`, `unix/signal_x86_64.c` L2612-2613).

    Those reject `boot`'s promise with the cut status, as any other `exit()` does.
  - `tw_process_exit` (`boot.c`) `longjmp`s to `boot`, which sets `depth` to 0 (`tw_depth_set`, `abi.md` v5, "Trampoline") and returns the status.
  - The `longjmp` unwinds the translated frames on the wasm stack as a wasm exception.
  - msvcrt has flushed stdout by then, in `LdrShutdownProcess` (`abi.md` v5, "Process exit").
  - The instance is finished after it, and a program runs in a fresh one.
- **Process exit from another thread (M4):** any thread may end the process. `RtlExitUserProcess` first kills the other threads through the server (`terminate_process`, `server/process.c` L1526, L933-950; section 7, "Signals to threads"), then shuts down and ends the process.
  - **On the main thread** `tw_process_exit` `longjmp`s to `boot`, as above.
  - **On any other thread** it records the status and `longjmp`s to that thread's `tw_thread_main` (section 9), which returns `TW_THREAD_PROCESS_EXIT`. `boot`'s promise then never settles.
  - **The JS host settles the process** with the first of: `boot`'s return, a thread's `TW_THREAD_PROCESS_EXIT` (the status from `tw_exit_status()`), or the rejection of any thread's promise (Emscripten's `ExitStatus`, or an error), which it treats as M3 treats `boot`'s. Then it clears its timers and never resumes a `green_block` again: the killed threads that were woken stay suspended, and nothing they would still do runs.
  - **Why not wake main and exit there:** FIFO would let the threads queued ahead of main run guest code after `ExitProcess`, and a pending `Sleep` timer would hold the host up to its deadline.
- **MEMFS gets the boot set** from the JS host before `boot`:
  - the prefix's `.reg` files, the `dosdevices` symlinks and `drive_c`'s directories, written up front;
  - the overlay, written up front;
  - the program, written up front in `drive_c`: `C:\tempwind\<name>.exe` by default (in M2, `tests/native`'s hello);
  - from M3, as lazy nodes: every closure PE file, rebased (`wine-build.md`, "Packaging"), and `closure.json`'s `data_files`. In M2 these were the two PE files the boot opens, the native tree's whole `nls/` directory and `wine.inf`, written up front.
  - from M3, the install copies. wineboot copies each builtin PE file into the prefix (`install_fake_dll`, `dlls/setupapi/fakedll.c` L938-975), and the prefix's `drive_c` keeps those files. For each of them whose name is a closure PE file's, the host makes a MEMFS symlink at its path to that file in the PE dir (`/wine/lib/wine/x86_64-windows/<name>`, a lazy node). It takes them from the prefix's `drive_c` listing, as it takes the directories. In `wine-4c6ec0d` that is 78 links: 66 in `windows/system32`, the 8 `.sys` files in `windows/system32/drivers`, `explorer.exe` in `windows`, and the `winsxs` copies of comctl32, msvcp90 and msvcr90. The prefix's own copies are never written.
    - **Why:** the PE loader loads a DLL only through a file. `find_dll_file` (`dlls/ntdll/loader.c` L3256) tries `\KnownDlls` (`open_known_dll`, L2747-2754), then searches the load path (`search_dll_file`, L3205; L3300-3305). Outside prefix bootstrap nothing finds a builtin without its file: `find_builtin_without_file` (L3132, L3144-3148) and the Unix side's `is_builtin_path` (`unix/loader.c` L1448-1454) act only then. Without the copies kernel32.dll isn't found, and the process exits with 0xc0000135 (WP5's first light).
    - **Then:** mapping the file's section reaches `load_builtin` (`unix/virtual.c` L3521-3526). For a `wine_builtin` image (`unix/loader.c` L1386-1390) it maps the builtin from the PE dir through `find_builtin_dll` instead, so the install copy gives the loader only a file to find and its header.
    - **Why symlinks, not the prefix's copies:** those are native Wine's build (kernel32.dll is 2.4 MB there and 0.9 MB in ours, with a different sha256). A symlink reaches the PE dir's lazy node, so it loads no extra bytes, and the module mapped is the PE dir's file, which the catalog matches.
    - **No `\KnownDlls`** (deferred, section 13): wineboot creates them (`create_known_dlls`, `programs/wineboot/wineboot.c` L997) and the wineboot skip doesn't, so the loader always searches the load path (`open_known_dll` fails, `dlls/ntdll/loader.c` L2747-2758, L3293-3298). A KnownDll in a program's own directory would then win over system32's, which natively it doesn't: Microsoft Learn's standard search order puts the KnownDLLs first. No M3 or M4 program ships one.

  `runtime/src/wine/boot-set.mjs` writes it and enters `boot`. The boot test records the files the boot opened.
- **Host files (M4):** a caller's files, written into `drive_c` with the boot set and read back after the run, so a program works on files as Phase 1's `run-pe --dir` let it.
  - **In:** `createWineProcess` takes `files`, a list of `{ path, bytes, mtime }` (`path` relative to `drive_c` with `/`, `mtime` in ms since the epoch) and empty directories `{ path, dir: true, mtime }`. The host writes each before `boot`, creating the parents, and sets its mtime (`FS.utime`), which Wine reads as the last write time (`get_file_times`, `unix/file.c` L1943-1949).
  - **Out:** after the process has settled, `collect(dir)` returns the tree under `drive_c/<dir>` in the same form, every file and directory with its bytes and mtime, in sorted path order. It reads MEMFS directly; nothing in the instance runs.
  - **`run-wine.mjs --dir HOST`** (Node) loads HOST's tree into `C:\work` and makes it the cwd (`--cwd C:\work`), then writes `C:\work` back to HOST when the run settles, whatever its outcome: new and changed files with their mtimes, new directories, and deletions. A host file the guest replaced by a directory, or the reverse, is removed first, then written. These are Phase 1's rules, so the 7-Zip matrix's steps behave as they did. Host names that are invalid on Windows, or that collide without case, fail at start with a usage error naming the file.
  - **In a Worker (M6)** the same `files` and `collect` work, with the bytes from the caller.
  - **Times:** MEMFS keeps milliseconds. The matrix's tree uses even seconds, so its times round-trip exactly.
- **Lazy nodes (M3):**
  - **The node:** a MEMFS node of our own. Its size comes from the boot-set manifest (path, size and sha256 per file; `wine-build.md`), so a `stat` works before the first read.
  - **The first read** loads the whole file: `fs` in Node, one synchronous XHR in a Worker.
  - **Why not `FS.createLazyFile`:** in Node, a `stat` of its node before the first read throws a `TypeError` (`research.md`, 2026-11-14). Wine stats first (`unix/file.c` L2970, `server/fd.c` L1999, `server/mapping.c` L1087 and L1158).
- **The browser host (M3):** in a Worker, `runtime/src/wine/web-files.mjs` gives `createWineProcess` the inputs that `node-files.mjs` gives it in Node, by URL from the static assets.
  - **Before `boot`** it fetches:
    - the modules: `wine-unix.mjs` and `.wasm`, `bridge.wasm`, and the run-time translator and floating-point helper;
    - `boot-set.json`, `catalog/catalog.json` and `prefix.json` (`wine-build.md`, "Layout under `target/wine`");
    - the prefix's top-level files and the overlay.

    The caller fetches the program and passes its bytes to `createWineProcess`, as in Node.
  - **On first use** it reads each lazy file, and each catalog module's `.wasm` and `.plan.json`, with one synchronous XHR (`xhrReader`, `lazy-node.mjs`), and compiles a module with the synchronous `new WebAssembly.Module`, which a Worker allows at any size.
  - **No sha256 check against the manifest** in the browser; Node checks on the first read. The program's sha256 comes from its own bytes, as in Node.

## 9. Blocking and threads (M4: green threads)
Line numbers are in `dlls/ntdll/unix/thread.c` unless another file is named; `sx.c` is `dlls/ntdll/unix/signal_x86_64.c`.

- **`green.c`:**
  - `green_block` is the only switch point. Around it, C saves and restores the spike's save set (`abi.md` v5, "Green threads"). `depth` joins the set in M3, through `tw_depth_get` and `tw_depth_set`.
  - It provides sleeping until a deadline, yielding, a wake queue, and from M4 signal delivery ("Signals" below).
  - Wine's blocking libc calls are routed there: `select` and `usleep` sleeps, `sched_yield`, `poll` on the server's pipes and the waits of section 7. A blocking call that green.c doesn't handle stops loudly.
    - green.c defines `select`, `poll`, `usleep`, `nanosleep` and `sched_yield` in place of libc's.
    - `select` with no fds, `usleep` and `nanosleep` sleep until their deadline; `poll` with no fds too. `poll` with a zero timeout probes (`__syscall_poll_nonblocking`). A `poll` or `select` that would block on fds stops loudly.
    - `sched_yield` lets the runnable green threads run first, spawned threads that haven't started included; with none, it returns at once.
    - The waits of section 7 wait on one wake queue, the server's wakeup pipes'. `send_thread_wakeup` wakes all of it; a woken thread reads its own pipe and waits again if it is empty.
  - **`green_wake` is idempotent (M4):** waking a thread that is already runnable changes nothing, and a thread is resumed once per `green_block`.
- **`green_pthread.c`**, the green pthread layer. The `-ww` libc that `-sSHARED_MEMORY` links without `-pthread` has no pthread functions at all (`research.md`, 2026-11-13):
  - mutexes (recursive ones included), condition variables, `pthread_once`, keys, `pthread_self` and the attribute functions;
  - keys are per green thread. `NtCurrentTeb()` (`thread.c`) reads `teb_key`, so it follows the running green thread;
  - a thread that suspends while it holds a mutex is a bug, and the layer asserts on it;
  - a condition wait goes through `green.c` (a wait that nothing can end is the scheduler's deadlock);
  - from M4: thread create, start, exit and join, and `pthread_sigmask` per thread (below). `pthread_detach`, `pthread_kill` and `pthread_cancel` stop loudly: Wine's ntdll, server and win32u never call them (grep).

**Threads (M4):**
- **Wine's thread:** `NtCreateThreadEx` makes the server's thread (`new_thread`), the TEB and stacks (`init_thread_stack`: a 1 MiB kernel stack below 4 GiB, L1209-1212), then `pthread_create(start_thread, teb)` with the kernel stack from `pthread_attr_setstack` and no guard (L1445-1450). `start_thread` (L1119-1132) sets the thread's `pthread_id` (L1128) and `teb_key`, runs `server_init_thread`, then `signal_start_thread`. win32u and the server start no threads; `loader.c` L2071-2074's is macOS's.
- **Create:** `pthread_create(thread, attr, start, arg)` makes a green thread with the next id (the main thread is 1), records `start` and `arg`, and takes its shadow stack from `attr`'s `pthread_attr_setstack` region (Wine's kernel stack), or 1 MiB from `malloc` if `attr` has none. It counts the thread as runnable, so `sched_yield` lets it start, and calls the import `green_spawn(id, top, bottom)` (`abi.md` v5, "Green threads"). It returns 0.
- **Start:** JS starts a spawned thread after the current call into the module returns, in order with the wakes (below): the stack limits to `(top, bottom)`, the stack pointer to `top`, then `tw_thread_main(id)` through `promising`.
- **`tw_thread_main(id)`** (a raw export) makes the thread current, sets `depth` to 0, takes it out of the runnable count, `setjmp`s and calls `start(arg)`. It returns 0 when the thread has ended, and `TW_THREAD_PROCESS_EXIT` when the process exited on it (section 8). It must not run on another thread's stack: JS has set the new stack first.
- **Per-thread state:** `virtual_alloc_teb` calls `signal_alloc_thread` (`unix/virtual.c` L4107), which allocates the thread's frame record (section 11) in its thread data. `signal_start_thread` builds the new thread's state block from its TEB as it builds the main thread's (section 8) and runs `tw_run_loop` on it. `virtual_free_teb` calls `signal_free_thread` (L4152), which frees both. The main thread's TEB comes from `virtual_alloc_first_teb`, which doesn't call `signal_alloc_thread`, so `signal_init_process` keeps allocating its frame record.
- **Exit:** Wine ends a thread in `pthread_exit` only, through `pthread_exit_wrapper` (L1103-1111), which closes the thread's fds first. Its callers are `exit_thread` (L1494-1514) and `abort_thread` (L1474-1479); a thread's start routine never returns, since `signal_start_thread` doesn't. `pthread_exit(ret)` records `ret`, tells the in-process server that the thread's request pipe closed (`inproc_thread_hangup`, section 7, "A thread's end"), wakes the thread's joiners and `longjmp`s to its `tw_thread_main`, unwinding its frames, translated ones included, as a wasm exception.
- **Join:** `pthread_join(t, ret)` waits on `t`'s end ("a thread's end" in the deadlock report), stores its value, and frees the green thread. Wine joins only from `exit_thread`: each exiting thread joins the previous one and frees that one's TEB and stacks (L1503-1510). So a stack region is released only after its thread has ended.
- **The main thread** runs on `boot`'s stack, Emscripten's own.
  - Its `pthread_id` stays 0: only `start_thread` sets it (L1128). `exit_thread`'s join skips a TEB whose `pthread_id` is 0 (L1507), so Wine never joins the main thread or frees its TEB. `pthread_join` of the main thread stops loudly.
  - `pthread_exit` on the main thread, which `exit_thread` reaches when it ends with other threads alive, makes the hang-up (section 7, "A thread's end"), then **parks** it: a `green_block` that nothing wakes. It never runs again. `boot`'s promise stays pending, and the process ends on another thread (section 8).
- **The last thread:** `exit_thread` and `abort_thread` end the process when `nb_threads` reaches 0 (L1501, L1477), and `RtlExitUserThread` turns the last thread's exit into `RtlExitUserProcess` (`dlls/ntdll/thread.c` L237-245). So every thread ending leaves a process exit, never a process without threads.
- **The schedule** stays deterministic: JS resumes woken threads and starts spawned ones in the order C woke or spawned them.

**Signals (M4), delivered at the wait:**
- **Sending:** `send_thread_signal` (section 7) marks the signal pending on the target green thread and wakes it if it waits.
- **Delivery points.** A pending signal that the thread's mask doesn't block is handled only:
  1. when the thread resumes in `green.c`'s wait or yield, after its waiter is unlinked (a new state, SIGNALED);
  2. in `pthread_sigmask`, when it unblocks the signal;
  3. before the syscall dispatcher returns to guest code (section 11): for a signal the running thread sent itself, or one that arrived while it ran.

  A handler never runs in the middle of other C code, so a waiter list never keeps a node from a stack that a handler unwound.
- **After a handler returns,** the wait it interrupted ends as an interrupted call: `select`, `poll`, `usleep` and `nanosleep` return -1 with `EINTR`, and a condition wait returns 0, a spurious wakeup. Wine's callers carry on: `NtDelayExecution` sleeps again for the time left (`unix/sync.c` L2463), `wait_select_reply` reads again (`unix/server.c` L377), and condition waits recheck their condition.
- **SIGQUIT** runs `abort_thread(0)`, the in-syscall path of `quit_handler` (`sx.c` L2608-2614). Our threads are always inside a syscall when they wait. It decrements `nb_threads`, ends the process if it was the last thread, and otherwise reaches `pthread_exit`. SIGQUIT is never blocked: it isn't in `server_block_set` (`unix/server.c` L1626-1633).
- **SIGUSR1** runs `usr1_handler`'s in-syscall branch (`sx.c` L2626-2669): the thread's context from its frame record (`NtGetContextThread`), `wait_suspend`, then `NtSetContextThread`. A suspended thread waits in `wait_suspend`'s server wait (L1532-1542), where a system APC runs too. SIGUSR1 is in `server_block_set` (L1631), which Wine blocks around server calls and in its exit paths, so it waits until Wine unblocks it.
  - On a unix call's frame, which is marked incomplete (abi.md v5, "Syscalls and unix calls"), the handler first clears the mark and sets the frame's EFLAGS to 0x200, as Wine does (`sx.c` L2640-2645): the state block's lazy flags are not materialized there. The handler's `NtSetContextThread` adds CONTEXT_CONTROL to `restore_flags`, so the dispatcher then takes its new-context return (section 11), to the same RIP and RSP.
- **The mask:** `pthread_sigmask` keeps one mask per green thread, in place of libc's single process-wide `sigprocmask`.
  - **Wine's calls** are ntdll's only (`unix/server.c` L308-310, L331, L342, L740, L774, L1634; `unix/thread.c` L1419, L1459, L1476, L1499, L1522, L1561, L1601). `config.h` renames `pthread_sigmask` to `tw_pthread_sigmask` (`green_pthread.c`), because libc's own stays in the link: Emscripten's `raise`, which the server's `kill` of its own pid and `alarm` reach (`imports.txt`), takes `__sig_is_blocked` from the same libc file, so a second definition would collide.
  - **`sigprocmask` stays libc's**, the server's own mask, as the server is another process natively. Its only caller is the server's change list, which blocks SIGIO around a list update (`server/change.c` L270-284); nothing sends SIGIO in-process.
  - **A new thread inherits its creator's mask,** as a pthread does. `NtCreateThreadEx` blocks `server_block_set` around `pthread_create` (`unix/thread.c` L1419-1459), so a new thread starts with SIGUSR1 blocked. The main thread blocks it in `server_init_process` (`unix/server.c` L1634). `signal_start_thread` unblocks `server_block_set` before the thread's first guest instruction, as `init_syscall_frame` does (`sx.c` L2978): that is the start's delivery point 2.
  - **A handler runs with `server_block_set` and its own signal blocked,** Wine's `sa_mask` without `SA_NODEFER` (`sx.c` L2862-2863), and the thread's mask is restored when it returns, as `sigreturn` does. So a SIGUSR1 sent while a thread is suspended in `wait_suspend` stays pending until its handler has returned.
- **Before a thread starts,** a signal sent to it stays pending until its first delivery point, after `start_thread` has set its TEB.
- **Who does what:** WP1 delivers SIGQUIT (no thread ends cleanly without it), WP4 SIGUSR1 and the masks.

**The JS scheduler** (`runtime/src/wine/`):
- When no green thread is runnable, it calls `tw_next_timeout()`, then `setTimeout` for that long, then `tw_run_timeouts()`, and resumes the woken threads.
  - `tw_next_timeout` counts thread waits and timers only. It ignores the server's KUSER tick (16 ms, `server/fd.c` L898) and its 30 s registry save (`save_timeout_user`, `server/registry.c`).
- **Spawned threads** start in the order of the spawns and wakes (above).
- **The scheduler's own stack (M4):** JS calls raw exports directly only when no thread runs (`tw_next_timeout`, `tw_run_timeouts`, `tw_exit_status`). Before each such call it sets the stack to a 64 KiB region it took from the raw `malloc` before `boot`, so no call runs on the stack of a thread that has ended, whose region Wine frees. A resumed thread restores its own stack in `green_switch`.
- **Nothing runnable and no timeout is a deadlock:** the scheduler stops loudly with each thread's wait. When `tw_next_timeout` returns -1 it prints each waiting green thread's wait on stderr (`tempwind: green: thread N waits on WHAT with no deadline`), and the parked main thread as `tempwind: green: thread 1 has exited (parked)`. The scheduler then makes each waiting thread's `green_block` throw an `Error` whose message starts with `tempwind: green: deadlock`, so its `promising` entry rejects.
- **Process exit** settles the process as section 8 says; after it the scheduler resumes nothing and starts nothing.

## 11. Syscalls, unix calls and contexts (M3, M4)
`src/signal_wasm64.c` and the generated `DIR/gen/syscall_table.c`. The boundary (addresses, entry, frame record, returns) is `abi.md` v5, "Syscalls and unix calls". This section is the C behind it. Line numbers are in `dlls/ntdll/unix/signal_x86_64.c` unless another file is named.

**The syscall table:**
- **Wine's list:** `dlls/ntdll/ntsyscalls.h` has the x86-64 entries `SYSCALL_ENTRY(id, name, argbytes)`, ids 0x0000-0x0101 (L270-527).
  - Two use variant macros (L295, L360), which L538-539 define as plain entries.
  - Wine's own table is `KeServiceDescriptorTable` (`unix/loader.c` L141-158).
- **The generator** (`gen-syscalls.mjs`) writes one wrapper per entry, `ULONG_PTR tw_sys_<name>(const ULONG_PTR *args)`, and the table of wrappers by number.
  - Each wrapper calls the real function with `args[i]` cast to the parameter's type from its `include/winternl.h` prototype, so the compiler does the conversions.
  - **Why wrappers:** Wine calls its table through a pointer with raw register arguments. In wasm a call through a pointer with another signature traps.
- **What it checks, failing the build otherwise (gate 4):**
  - every entry other than a stub has a prototype, and its parameter count equals `argbytes / 8`;
  - every parameter is a scalar or a pointer, except `NtSetLdtEntries`'s two `LDT_ENTRY`s, passed by value (`winternl.h` L4797). The wrapper copies each from its 8-byte argument;
  - every return type is `NTSTATUS`, except `NtGetCurrentProcessorNumber`'s `ULONG`, which the wrapper zero-extends.
- **The six stubs:** `ALL_SYSCALL_STUBS` (`ntsyscalls.h` L531-537) are `static void name(void)` functions that raise a Wine stub exception (`unix/loader.c` L115-139). Their wrappers stop loudly with `tempwind: unsupported: syscall <name>` until M5.
- **Table 1, win32u's (M4):**
  - **Wine's:** win32u's unix call 0, `init`, registers its table with `KeAddSystemServiceTable(syscalls, NULL, ARRAY_SIZE(syscalls), arguments, 1)` (`win32u/syscall.c` L92-106; `unix/loader.c` L625-634). The table has 1,540 x86-64 entries, `SYSCALL_ENTRY(id, name, argbytes)` (`win32syscalls.h` L1545-3085).
  - **1,062 of them are stubs** (`ALL_SYSCALL_STUBS`, `win32syscalls.h` L3089): `static void name(void)` functions that raise a Wine stub exception (`win32u/syscall.c` L39-61). Their wrappers stop loudly with `tempwind: unsupported: win32u syscall <name>` until M5, as table 0's six do.
  - **The other 478** have prototypes in `include/ntuser.h` and `include/ntgdi.h`, none with a struct or a float passed by value. The generator writes their wrappers as for table 0, with every return narrower than 64 bits zero-extended and a `void` return as 0, into a second table, `tw_win32_syscall_*`, in the same file.
  - **Gate 4 for table 1:** every entry is either a stub or has a prototype whose parameter count equals `argbytes / 8`, and every parameter is a scalar or a pointer. The generator prints the split, 1,062 and 478.
- **Tables 2 and 3** stay empty.

**Dispatch** (`tw_syscall_dispatcher`):
1. Refresh KUSER's clock: the in-process server's `set_current_time` (`server/fd.c` L418-426), which writes KUSER's time fields.
2. Build the frame record (`abi.md` v5).
3. Decode the id. A bad one returns `STATUS_INVALID_SYSTEM_SERVICE`, as Wine's does (`signal_x86_64.c` L3325): a number at or above the table's `ServiceLimit`, or table 1 before `KeAddSystemServiceTable` has registered it (its limit is 0 until then), or table 2 or 3. Once table 1 is registered, its limit must equal the generated table's size, or the dispatcher stops loudly.
4. Gather `argbytes / 8` arguments into an array: R10, RDX, R8, R9, then the stack.
5. Trace as Wine does when `WINEDEBUG` turns the `syscall` channel on: `trace_syscall` before the call and `trace_sysret` after it (`unix/loader.c` L636-664; Wine calls them at L3160-3161 and L3293-3322).
6. Call the wrapper, and return by `restore_flags`.

**Unix calls** (`tw_unix_call_dispatcher`):
- The handle must be the address of `unix_call_funcs` the Unix side stored in `__wine_unixlib_handle` (section 8), and the code must be below its 8 entries (`unix/loader.c` L1132-1142). From M4 the handle may also be win32u's table, which `tw_unixlib_funcs` returned (section 2), with the code below its count. Anything else stops loudly.
- The call is `unix_call_funcs[code](args)`, with `args` a guest pointer, which C can use as it is.
- It returns as a syscall does.

**The frame record per thread:**
- Wine keeps a `struct syscall_frame` per thread (L462-495), which `get_syscall_frame()` returns.
- Our thread data holds the thread's state-block pointer and the frame's other fields: `restore_flags` and the syscall id. The context functions work on the state block.

**Contexts,** ported for the current thread:
- **`NtGetContextThread`** (L1215-1346) reads the state block:
  - CONTROL: Rip, Rsp and EFlags (materialized at entry), SegCs 0x33, SegSs 0x2b;
  - INTEGER: the GPRs;
  - SEGMENTS: the selectors of section 3;
  - FLOATING_POINT: `FltSave` and `MxCsr`;
  - DEBUG_REGISTERS: zeros;
  - XSTATE: none, since the profile has no AVX.
- **`NtSetContextThread`** (L1116-1208) writes the fields its flags name into the state block. It then sets `restore_flags |= flags & ~CONTEXT_INTEGER`, as Wine does (L1206).
- **`signal_set_full_context`** (L1083-1090) adds `CONTEXT_INTEGER` to `restore_flags` when the context carries all integer registers.
- **`NtContinue`** is Wine's own `NtContinueEx` (`unix/server.c` L848-865): an alertable call polls for APCs with a zero timeout, then calls `signal_set_full_context`.
- **The FP conversion,** both ways:
  - FCW, FSW and MXCSR, with `MxCsr_Mask` = `TW_MXCSR_MASK`;
  - the abridged tag byte: bit p set when R[p] isn't empty. Going back, each register's full tag comes from its contents by the translator's rule (`translator.md`, "x87", Tags);
  - `FloatRegisters[i]` = ST(i) = R[(TOP + i) mod 8];
  - XMM0-15.

  It must agree with the translator's `fxsave` (`translator.md`, "fxsave m512"), so a guest `fxsave` and `NtGetContextThread` report the same.
- **Signals at the dispatcher's return (M4):** before either dispatcher returns to guest code, a pending signal that the thread's mask doesn't block is handled (section 9, delivery point 3). SIGUSR1's handler takes the context from the frame record and the state block, so a thread that suspended itself resumes with what it was about to return.

**User APCs (M4, WP4):**
- **Wine's path:** an alertable wait returns `STATUS_USER_APC` with the APC (`server/thread.c` L1189; `unix/server.c` L719-818), and the Unix side calls `call_user_apc_dispatcher` (L1661-1705). It builds an `apc_stack_layout` below the context's RSP (or the frame's), with the context, the continue arguments, the APC's arguments in `P1Home`-`P4Home` and a machine frame, then points the frame at it: `rsp` = the layout, `rip` = `pKiUserApcDispatcher`, `rbp` = the context's, and `restore_flags |= CONTEXT_CONTROL`. It returns the status.
- **Ours:** the same, against the state block: RSP, RIP and RBP are written there, and `restore_flags |= CONTEXT_CONTROL` makes the dispatcher take its new-context return (`abi.md` v5, "Syscalls and unix calls"), with RAX = the status. PE `KiUserApcDispatcher` then calls the APC and `NtContinueEx` (PE `signal_x86_64.c` L382-415), which resumes the saved context as M3's `NtContinue` does.

**Suspension and another thread's context (M4, WP4):**
- **Wine's path:** `NtSuspendThread` and the context calls on another thread reach the server's `suspend_thread` and `get_thread_context`/`set_thread_context`, which call `stop_thread` (`server/thread.c` L955-971, L2199-2230). It sends SIGUSR1 (section 7). The target's `usr1_handler` posts its context to the server through `wait_suspend`'s server wait (section 9), and the caller gets it from the server.
- **Ours:** `NtGetContextThread` and `NtSetContextThread` on another thread take Wine's path for a handle that isn't the current thread (L1116-1208, L1215-1346): the server request, and the wait when the target hasn't stopped yet. The target stops at its next delivery point. A suspended start runs `wait_suspend` before the thread's first guest instruction (`sx.c` L2957; `unix/thread.c` L1532-1542).
- **What the server keeps:** the context the target posted is the one its state block held at the delivery point, so another thread's Get and Set round-trip the target's registers.

- **Still stopping loudly:**
  - the exception paths (`call_user_exception_dispatcher`, `NtRaiseException`): M5;
  - `KeUserModeCallback` and `NtCallbackReturn` (`sx.c` L1905-1931): deferred (section 13). win32u's first callback is in `register_builtins` (`win32u/class.c` L1225-1240), reached only through `get_desktop_window` (`winstation.c` L898) or a desktop-class window (`window.c` L5528); a console program's user32 attach reaches neither (`dlls/user32/user_main.c` L204-257).

## 12. The run loop and translated code (M3)
`src/run.c` and `src/boot.c` in C, and the JS host in `runtime/src/wine/`. The boundary is `abi.md` v5, "Wine boundary".

**`tw_run_loop(state)`** (`tempwind_private.h`):
- It calls `tw_run(state)` until the thread ends, and acts on each exit reason:
  - **`EXIT_LEFT_CODE`:** it finds the run of committed, executable pages around `rip` inside its view (`tw_exec_range`, patch 0106: `VPROT_EXEC`, no guard pages), and calls `tw_translate(rip, base, size)` with it.
    - With no such run, it stops loudly. On Windows that is an execute access violation, which M5 raises.
    - If `tw_translate` fails, it stops loudly.
  - **`EXIT_HOST`:** the host function that stopped recorded why in C, and the loop returns it to its caller. In M3 and M4 nothing stops that way (a thread ends by `pthread_exit`, section 9), so a thread's loop that returns stops loudly.
  - **`EXIT_FAULT`:** stops loudly. M5 raises the exception through Wine's dispatcher.
  - **`EXIT_UNSUPPORTED`:** stops loudly. That includes store-check hits.
- **The loud stops** print `tempwind: unsupported: run <exit> rip=<hex>`, the fault address and kind, then the page-state byte and Wine's protection byte of one address, then `abort()`. That address is the fault address for `EXIT_FAULT`, and `rip` for any other exit: `EXIT_UNSUPPORTED` records no address, a store-check hit's included (`translator.md`, "Memory checks"), so `rip` is the store's.

**One process, in order** (the JS host):
1. Create the shared memory (4 GiB initial, 16 GiB maximum), `env.table` (at least `TW_TABLE_RESERVED` slots) and `env.depth` (0).
2. Instantiate the bridge (`abi.md` v5, "The bridge").
3. Instantiate the Unix side. Its imports are:
   - `tw_run`, `tw_depth_get`, `tw_depth_set` and `tw_flags_materialize`, from the bridge;
   - the JS imports.
4. Allocate the lookup header and slots with the raw `malloc`, and get the page-state table from `tw_page_flags()`.
5. Install `tw_syscall_dispatcher` and `tw_unix_call_dispatcher` in `env.table`, and insert their lookup slots.
6. Write the boot set, `chdir` to the program's directory, and enter `boot(argc, argv, 0)` through `promising`.

From then on JS links modules on demand: an AOT module through `tw_image_mapped`, a run-time one through `tw_translate`.

**Linking** (JS, both kinds):
- Grow `env.table`, and instantiate the module with `env.memory`, `env.table`, `env.table_base`, `env.lookup`, `env.depth`, `env.page_flags` and the `fp` namespace.
- Insert its blocks (first translation wins), and set `PAGE_CODE` on its code pages.
- The first module linked replaces the bridge's placeholder at `TW_RUN_INDEX` with its `run`.
- **AOT modules:** the catalog has one per rebased closure file and per test program (`wine-build.md`, "Packaging"). It is linked when the image is mapped at the catalog's base and the file's sha256 matches.
- **Run-time modules:** `tw_translate` reads the range's bytes from guest memory and calls the run-time translator with `null_check`, `store_check` and `shared_memory`. The known addresses it passes are the linked blocks inside the range.
- **Both memory checks are on** in every module of a Wine process (`guest-memory.md`, "Phase 2 defaults"):
  - a NULL access exits with `EXIT_FAULT`;
  - a store to a `PAGE_CODE` or `PAGE_WATCH` page exits with `EXIT_UNSUPPORTED`.
  - Both stop loudly in M3.
- **What the host reports at exit:** the AOT links, the fallbacks (images without an AOT module, and each run-time translation), and the bytes the lazy nodes loaded.

**`depth`:**
- It starts at 0.
- `boot` resets it after the exit `longjmp` (section 8).
- `green_block` saves and restores it around each switch from M3 on (section 9). M4's threads are the first to switch between threads with guest frames on their stacks.
- A new thread starts at 0 (`tw_thread_main`), and a thread's `longjmp` out of its frames (exit, process exit) leaves nothing behind: the next thread to run restores its own.

## 13. Later
- **Deferred by the owner (2026-11-21):**
  - **`\KnownDlls`:** to M5, if conformance shows the difference. The loader then searches the load path (section 8). Creating them needs `wineboot`'s `create_known_dlls` (`programs/wineboot/wineboot.c` L997-1046) or our own copy of it, with ranged lazy reads so the sections don't load whole files.
  - **Services:** to Phase 4, with child processes. Natively a session's first process runs `wineboot --init` (`unix/env.c` L1539-1561), which starts services.exe (`wineboot.c` L1898-1906); our boot skips it (section 8). combase starts RpcSs only on `RPC_S_SERVER_UNAVAILABLE` (`dlls/combase/rpc.c` L185-206), which needs a child process.
  - **`KeUserModeCallback` and `NtCallbackReturn`:** to Phase 3's desktop, or to M5 if a conformance unit needs them first. Their loud stops stay (section 11).
- **M5:** exceptions: the basic raise path. `EXIT_FAULT` raises, and the syscall stubs of both tables raise as Wine's do.
- **Phase 4:**
  - a store to translated code invalidates and resumes;
  - a store-check hit on a write-watched page records the write;
  - guard pages;
  - threads on more than one core.
- **KUSER's clock** advances only at syscall entries, server requests and green switches (`signal_wasm64.c` L239, section 7). A guest that only reads KUSER sees time stand still between syscalls; kernel32's `GetTickCount` is such a read (`dlls/kernel32/sync.c` L85-105). CoreMark and `7z b` time with QPC, a syscall (`ntdll/time.c` L383-388 → `unix/sync.c` L2473-2478), and `7z b`'s `GetTickCount` comes with `GetProcessTimes`, another syscall (`research.md`, 2026-11-21). WP5 checks for a loop that reads `GetTickCount` with no syscall in it; one it finds gets a ticker.
- **The boot's sysparams cost:** the volatile sysparams key is new at every boot of the in-process server, so win32u writes its default entries at every boot (`win32u/sysparams.c` L5897-5900). WP5 measures it.

## Risks
- **The first full link** may need many stubs and renames. WP1 reports at its first full link, before the gates are clean.
- **Emscripten's pipes are unbounded in 6.0.12.** 7.0.0 caps them at 64 KiB; the server's partial-write path for a larger reply would then need `main_loop`. We stay on 6.0.12 (`research.md`).
- **A 4 GiB initial memory** must be cheap to create in Node and in a Chromium Worker (pages reserved, not committed). WP0 measures it.
- **Signals only at the wait (M4):** a thread handles SIGQUIT and SIGUSR1 at a wait, at an unblock or at the dispatcher's return, never in the middle of C code. Natively a handler can run anywhere outside the blocked set. A program that suspends a thread spinning in guest code without syscalls would wait until that thread's next syscall or switch; none of M4's programs does.
- **win32u's first link (M4)** may need many stubs, renames and `config.h` lines. WP2 reports at its first full link, before the gates are clean.
- **The session cap (M4):** 16 MiB of the host heap is about 12 times the first block, 1,327,104 bytes: Wine sizes it for the user handle table (`session_shm_t`, 1,047,808 bytes) and 512 objects of 544 bytes (`server/mapping.c` L1344-1347). With the growth rule (L1382) the reservation holds six growths, to 14.4 MiB; a console program makes a handful of objects. Growth past it stops loudly rather than moving the memory win32u already points into.
