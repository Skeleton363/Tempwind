# Wine's Unix side with Emscripten (v1, Phase 2 M2)

Wine 11's ntdll Unix part and wineserver, built with Emscripten as one wasm64 module that runs in the Windows process's Worker. This is the contract for M2's work packages and the base M3-M5 build on. The boundary to translated code is `abi.md` v5, "Wine boundary"; the address space is `guest-memory.md`; the Wine CI build and its published data are `wine-build.md`. The decisions behind it are in `docs/status/phase-2.md`, and the research in `docs/dev/research.md` (2026-11-06 and 2026-11-13).

Line numbers refer to the pristine wine-11.0 tarball.

## 1. Tree
```
native/wine/                 LGPL-2.1-or-later (COPYING.LIB, README.md)
  build.sh                   the build (section 2)
  config.h                   hand-curated configure result for Emscripten 6.0.12
  imports.txt                the wasm imports the module may have, each with a reason
  rename-server.h            renames the server's colliding globals (section 2, gate 3)
  patches/NNNN-area-what.patch
  include/tempwind/abi.h     generated by `x64wasm-cli gen-header` (abi.md v5), committed
  src/                       our new files (LGPL)
  prefix/overlay.reg         wineboot's per-boot keys (section 8)
  tests/                     C harnesses (section 10)
runtime/src/wine/            the JS host (ours, all rights reserved)
tests/wine/                  Node tests, prepare.sh, kuser-dump.c
```
- **Patches** are diffs against the pristine tarball (`patch -p1`), applied in name order with no fuzz. Each starts with a header: what it changes and why, and the section of this file it implements.
- **The number range names the owner:** `00xx` build and headers, `01xx` the virtual backend, `02xx` the server, `03xx` ntdll startup. A later patch may touch a file an earlier one touched; the later range's owner then owns that file from the merge of the earlier work package on.
- **`src/`:**
  - `boot.c`: the `boot` export and the startup glue (section 8);
  - `green.c`: blocking, sleeping and waking (section 9);
  - `green_pthread.c`: the pthread functions Wine calls (section 9);
  - `inproc.c`: the in-process server transport (section 7);
  - `signal_wasm64.c`: the machine layer that replaces `signal_x86_64.c`. In M2: the process and thread setup of section 8, and stubs that stop loudly for the rest (`NtCurrentTeb()` is `thread.c`'s, which reads `teb_key`);
  - `stubs.c`: libc functions Emscripten lacks (section 2);
  - `version.c`: the version strings Wine's build would generate;
  - `virtual_wasm.c`: the memory backend under `virtual.c` (sections 5 and 6);
  - `library.js`: the `--js-library` that declares the imports of `abi.md` v5;
  - `tempwind_private.h`: what the `src/` files share (`tw_unsupported`, the imports, the green thread and queue, `grow_to`).
- **Our patches and `native/wine/` stay public under the LGPL.** The JS host and the tests are our own code.

## 2. Build
`native/wine/build.sh [--out DIR] [--jobs N] [--census]` (default `DIR` = `target/wine-unix`). Everything it makes goes under `DIR`, so two builds with different `--out` don't collide.
1. **Source:** the tarball named under `"wine"` in `tests/targets/sources.json`, downloaded from its URL into `DIR/src/` (or reused there) and checked against the pinned sha256. It extracts only what it compiles: `dlls/ntdll/unix/`, the ntdll headers they include, `server/` and `include/`.
2. **Patches** from `native/wine/patches/`, in name order. A patch that doesn't apply cleanly fails the build.
3. **Compile** every C file through `scripts/emcc.sh`:
   - ntdll's Unix part: the `UNIX_SRCS` of `dlls/ntdll/Makefile.in`, except `signal_*.c`, which `src/signal_wasm64.c` replaces;
   - the server: the `SOURCES` of `server/Makefile.in`, with `-include rename-server.h`;
   - `src/*.c`.

   The flags: `-m64 -O2 -sSHARED_MEMORY -fwasm-exceptions -sSUPPORT_LONGJMP=wasm -DWINE_UNIX_LIB -include native/wine/config.h`, the defines Wine's makefiles give each directory (`EXTRADEFS`), and Wine's include paths, with `native/wine/include` first. `-sSHARED_MEMORY` at compile time turns on atomics and bulk memory, which the shared-memory link requires of every object (wasm-ld refuses an object without them).
4. **Link** `DIR/wine-unix.mjs` and `DIR/wine-unix.wasm` with the spike's flags (`abi.md` v5, "Instances") and these:
   - `-sINITIAL_MEMORY=4GB` (section 5);
   - `-sSTACK_SIZE=1MB -sSTACK_OVERFLOW_CHECK=2`: with `GLOBAL_BASE` the layout is data, then the stack, then the heap, so the stack grows down into Wine's globals;
   - `-Wl,--wrap=sbrk` (section 5);
   - `-Wl,--fatal-warnings`;
   - `-Wl,--no-gc-sections`: every compiled function stays in the module, so gate 1 covers all of Wine's code. With section GC, wasm-ld drops what the entries don't reach and doesn't report the undefined symbols of dead code; while `boot` and the server's entry are skeletons, that is nearly all of Wine (the first link: a 19 KB module).
   - `-sEXPORTED_RUNTIME_METHODS=FS,ENV`;
   - `-sEXPORTED_FUNCTIONS=` the host entries of `abi.md` v5;
   - `--js-library native/wine/src/library.js`.

   Each `native/wine/tests/NAME.c` links with the same objects into `DIR/test-NAME.mjs` and `.wasm`, with `tw_test_main` exported in place of `boot`.
5. **Gates.** Each failure names what to fix:
   1. **No undefined symbols.** The link keeps Emscripten's default `ERROR_ON_UNDEFINED_SYMBOLS=1`: no `-sERROR_ON_UNDEFINED_SYMBOLS=0`, no `--allow-undefined`, no `-sWARN_ON_UNDEFINED_SYMBOLS`.
   2. **Imports:** every import of every module built (module and field, read from its import section) is listed in `imports.txt`. A new import needs its line, with a reason, in the same change.
   3. **Collisions:** `emnm` over the server's objects and over ntdll's (with `src/`) finds no global symbol defined on both sides that `rename-server.h` doesn't rename. `--census` prints the list, so the header can be regenerated from it.
6. **`DIR/build-info.json`:** the emcc version, the tarball's sha256, each patch with its sha256, the import list, and the sizes of `wine-unix.wasm` raw and gzipped.

**`config.h`** is a non-Linux POSIX profile. Every `HAVE_` it defines is true of the 6.0.12 sysroot: the header exists and the function links. Anything Linux-only (`__linux__` branches, `prctl`, `epoll`, `inotify`, futexes) stays off.

**`stubs.c`:** a function Wine calls that the sysroot lacks gets a stub here. Each stub says why. It either fails with an errno that Wine's caller handles, or stops loudly with `tempwind: unsupported: <name>` on stderr and `abort()`. A stub never pretends to succeed.

**In CI**, `.github/workflows/wine-unix.yml` runs `build.sh`, then `npm run test:wine`, and publishes `wine-unix-<sha7>` with `scripts/release-publish.sh`: `wine-unix.mjs`, `wine-unix.wasm`, the test modules and `build-info.json`. `tests/targets/wine-unix.lock` names the release that tests use when they don't build. In a session, `build.sh` runs through Docker (`docs/dev/commands.md`).

## 3. The guest is AMD64
- **The module is wasm64; the Windows it describes is x86-64.**
  - A `__x86_64__` branch that describes the **guest** gets `|| defined(__wasm64__)`: Windows structures, `CONTEXT`, the TEB and PEB layouts, the PE machine, `is_win64`, the syscall frame's layout.
  - A branch that describes the **host CPU** doesn't: inline assembly, signal contexts, `cpuid`, `xgetbv`, `fxsave`, `rdtsc`, the host page size. It gets a wasm64 path or a stub.
- **`_WIN64`:** `include/basetsd.h` defines it for `__wasm64__`, as for `__x86_64__`.
- **`C_ASSERT`s** in `src/version.c`: `sizeof(ULONG_PTR) == 8`, `sizeof(INT_PTR) == 8`, `sizeof(CONTEXT) == 0x4d0`, and the `CONTEXT` offsets the boot test reads.
- **CPU information comes from the translator's profile** (`abi.h`, section "CPUID"):
  - `system.c`'s `do_cpuid` reads `TW_CPUID_LEAVES`. Other leaves return zeros, as the translator's `cpuid` does.
  - `do_xgetbv` returns `TW_XCR0`. Wine never reaches it, since the profile has no OSXSAVE.
  - The `fxsave` DAZ probe reads `TW_MXCSR_MASK`, what the translator's `fxsave` stores (0xFFFF).
  - `NumberOfProcessors` and the active processor mask are 1.
- **Segment selectors:** `cs64_sel` = 0x33 and `ds64_sel` = 0x2b, the x86-64 user selectors; the thread's FS selector is 0 (no WoW64).

## 4. Address map and image placement
`guest-memory.md`, "Address map of one process", is the layout. What it means for Wine's code:
- **Wine allocates only in the guest regions.** The preloader's reserve list becomes a static list: [0x10000, 0x7ffe_0000), [0x7ffe_0000, 0x7fff_0000) for KUSER and the syscall slot, and [0x1_0000_0000, 0x4_0000_0000). The NULL region, the gap, the host region and everything above 16 GiB are outside it, so `NtQueryVirtualMemory` reports them as reserved.
- **Limits:** `address_space_limit`, `user_space_limit`, `working_set_limit` and `host_addr_space_limit` are 0x4_0000_0000 (`virtual.c` L191-199). `user_space_limit` drops to 0x7fff_0000 for an EXE without `LARGE_ADDRESS_AWARE`, as in Wine. `address_space_start` is 0x110000, Wine's x86 value, which keeps the DOS area clear.
- **Wine's own bookkeeping lives in the host heap:** the virtual heap (`alloc_virtual_heap`, L3600), `pages_vprot` and the view tree. None of it is in a guest region.
- **The host region** [0x8000_0000, 0x1_0000_0000) belongs to the Unix side's allocator: Emscripten's static data from `GLOBAL_BASE`, the 1 MiB stack, then the heap up to 0x1_0000_0000. The runtime's data in it (state blocks, the lookup table, the page-state table) comes from the raw `malloc` export.
- **Images:**
  1. An image maps at its preferred base when [base, base + size) is free and inside a guest region. `map_image_view` tries the preferred base first for every image.
  2. Only if that fails does a DLL marked `ImageDynamicallyRelocated` ask the server (`get_image_map_address`, `virtual.c` L3403).
  3. Otherwise `map_view` searches the guest regions, top-down for relocated DLLs, as Wine does.
  - **The server's ranges** (`server/mapping.c` `init_memory`, L271-276): `ranges64` is [0x1_0000_0000, 0x1_7000_0000), assigned top-down, so the first slot ends just below ntdll's base and the memory stays small. `ranges32` stays [0x6000_0000, 0x7c00_0000).
  - **The same files in the same load order land at the same addresses.** Nothing is randomized.
  - This differs from native Wine, which moves every `ImageDynamicallyRelocated` DLL into its ASLR range (`research.md`, 2026-11-13). M3 decides with the translator's evidence whether the closure DLLs are rebased to unique bases when packaged.

## 5. Memory growth
- **One grower:** `virtual_wasm.c`'s `grow_to(end)` is the only `memory.grow` in the module. It grows the memory to cover `end`, rounded up to 64 KiB and never past 262144 pages, then calls the import `memory_grown`. A grow that fails makes the map fail with `ENOMEM`.
- **The heap never grows the memory.**
  - `INITIAL_MEMORY` is 4 GiB, so the memory covers the whole host region from the start.
  - `__wrap_sbrk` refuses any increment that would move the break past 0x1_0000_0000: it returns `(void *)-1` with `errno = ENOMEM`, and `malloc` returns NULL.
  - `emscripten_resize_heap` is therefore never reached. This settles the spike's first open item (`abi.md` v5).
- **The harness checks it:** after the backend has grown the memory past 4 GiB, a `malloc` that would cross 0x1_0000_0000 returns NULL, and the memory's size is unchanged.

## 6. The virtual backend
`virtual_wasm.c` replaces the host calls in `virtual.c`: `mmap`, `munmap`, `mprotect`, `madvise`, `msync` and the `anon_mmap_*` helpers. `01xx` routes them there.
- **Maps:**
  - a fixed map (`anon_mmap_fixed`) grows the memory to cover the range and zeroes it;
  - a try-fixed map (`anon_mmap_tryfixed`) does the same, but fails with `EEXIST` if any page of the range is already mapped;
  - a map at no fixed address takes a free range in the guest regions;
  - Wine's decommit is a fixed map, so a recommitted page reads zero;
  - `mprotect` is bookkeeping only. Wine keeps the protections itself, and nothing faults;
  - `munmap` marks the range free; the memory never shrinks.

  The backend keeps its own record of mapped ranges, in the host heap.
- **File views are copies.**
  - A view copies the file's bytes into the range.
  - A writable **shared** view keeps the file (a `dup` of its fd), offset and size. It writes the bytes back on `NtFlushVirtualMemory` and on unmap.
  - A second writable shared view of a file range that already has one stops loudly (`tempwind: unsupported: second writable view`). Read-only and copy-on-write views can be copied any number of times.
  - Image sections are copies too.
  - (M4) the session shared memory gets the same treatment.
- **KUSER:**
  - `virtual_alloc_first_teb` commits the page at 0x7ffe0000, as in Wine;
  - `virtual_map_user_shared_data` maps nothing: the guest and the in-process server share that one page;
  - `virtual_init_user_shared_data` writes to 0x7ffe0000 directly, not through a second mapping.
- **The page-state table** (`abi.md`, "Page-state table"):
  - the backend allocates it (1 byte per 4 KiB page up to 16 GiB, 4 MiB, from the host heap) and exports its address as `tw_page_flags()`;
  - the backend keeps `PAGE_WATCH`: it is set on the pages of a write-watch view whenever Wine sets `VPROT_WRITEWATCH` there (commit, `NtResetWriteWatch`), and cleared whenever Wine clears it (a recorded write);
  - the JS linker sets `PAGE_CODE` (M3).
- **Pointer validation:** a bad guest pointer doesn't fault, so the three `__TRY` sites in `virtual.c` become checks against the views:
  - `virtual_check_buffer_for_read` (L4807): every page is committed and readable, not a guard page;
  - `virtual_check_buffer_for_write` (L4841): every page is committed and writable or write-copy;
  - `NtReadVirtualMemory` (L6693): the same read check on the source.

## 7. The in-process server
The server is linked into the module and runs on the calling thread. `02xx` and `src/inproc.c`.
- **Wine's pipes and fd bookkeeping stay**, over Emscripten's pipes.
  - After `send_request` (`dlls/ntdll/unix/server.c` L183) writes a request, the client calls the server's `read_request` (`server/request.c` L328) for its own thread, synchronously. The handler runs, and `send_reply` writes the reply to the pipe.
  - The client reads the reply as Wine does (`wait_reply`, L276).
- **Waits:**
  - a `wait_fd` read that gets `EAGAIN` blocks in `green_block` until the thread is woken;
  - `send_thread_wakeup` (`server/thread.c` L1196) also wakes the green thread.
- **fds:**
  - `thread_get_inflight_fd` `dup()`s the client's fd, since each side closes its own copy;
  - `send_client_fd` puts a `dup` of the fd on a queue, and `wine_server_receive_fd` takes it from there;
  - `create_process` gets one end of a pipe for `msg_fd`.
- **Start:** `server_init_process` starts the server in place of `server_connect`, after KUSER is committed. It runs what the server's `main` would:
  - `set_current_time`;
  - `init_memory`, with the page size 0x1000 and the ranges of section 4;
  - `init_directories(load_intl_file())`, with `l_intl.nls` from the constant path of section 8;
  - `init_threading` and `init_registry`.

  Then it creates the process and its first thread as `master_socket_poll_event` does (`server/request.c` L543), and the client receives the request fd from the queue.
- **KUSER:** the server's `user_shared_data` pointer is 0x7ffe0000 (`server/mapping.c` L1502).
- **Not in-process:** the master socket, the lock file, daemonizing, signal handling and `main_loop`. An fd event that only `main_loop` would deliver stops loudly.
- **Time:** `set_current_time` runs at every request and at every green switch.
- **Kills:** the SIGQUIT kill of a thread (`server/thread.c` ~L1627) becomes an exit path that ends the green thread (M2: the process).
- **Registry saves** go to MEMFS as in Wine (on its timer and at exit). MEMFS is not persisted in M2.

## 8. Startup
`src/boot.c` and `03xx` (`loader.c`, `env.c`, `server.c`, `system.c`, `thread.c`).
- **Entry:** `boot(argc, argv, flags)`, a raw export entered through `WebAssembly.promising` (`abi.md` v5). JS writes argv into the host heap through the raw `malloc`.
  - `argv[0]` is `/wine/bin/wine`, `argv[1]` the program as a DOS path (`C:\tempwind\hello.exe`), then its arguments.
  - `boot` records the launch directory, then runs Wine's `__wine_main`.
  - `flags`: `BOOT_STOP_AT_ENTRY` (1) is the only mode in M2. M3 adds running.
  - It returns 0 once it has stopped at the entry. A Wine error ends in `exit()`, which the host sees as the rejection of `boot`'s promise with Emscripten's exit status.
- **The environment,** set by the JS host in `preRun` (libc builds `environ` from `ENV` during instantiation):
  - `WINEPREFIX=/home/runner/wine-prefix`, the path the prefix was made at (`wine-prefix.path`), since its `.reg` files hold it;
  - `HOME=/home/runner`, `USER=runner`, `LANG=en_US.UTF-8`, `TZ=UTC`;
  - `WINEDEBUG` passed through from the host.
- **Paths:** `init_paths` (`loader.c` L449) uses constant paths instead of `dladdr`: `/wine/lib/wine/x86_64-windows` for the PE files, `/wine/share/wine` for NLS and `wine.inf`, `/wine/bin` for the loader. `get_initial_directory` (`env.c` L1389) uses the launch directory `boot` recorded, not `getcwd()`, because the server moves the cwd.
- **stdio:** fds 0-2 are non-tty character devices that the JS host provides (no line buffering, `isatty` false), so `get_initial_console` (`env.c` L1340) passes them to the server as plain handles and kernelbase starts no conhost.
- **The wineboot skip:** in place of `run_wineboot` (`env.c` L1537), boot creates `\KernelObjects\__wineboot_event`, runs `virtual_init_user_shared_data()`, writes wineboot's seven KUSER fields (NtBuildNumber, NtProductType, ProductTypeIsValid, NtMajorVersion, NtMinorVersion, SuiteMask, NtSystemRoot) from the PEB's version as `create_user_shared_data` does (`programs/wineboot/wineboot.c` L319), then sets the event.
- **The overlay:** `native/wine/prefix/overlay.reg`, loaded right after `user.reg`. It holds the computer name, the hardware description with the CPU from the profile, and the volatile environment.
- **No child processes:** `NtCreateUserProcess` returns `STATUS_NOT_SUPPORTED` and prints `tempwind: unsupported: NtCreateUserProcess <image>`.
- **The host-pointer slots in ntdll.dll:** `load_ntdll_functions` writes the poison value `TW_NO_DISPATCHER` (`abi.h`, non-canonical) into `__wine_syscall_dispatcher` and `__wine_unix_call_dispatcher`, and `signal_wasm64.c` commits the page at 0x7ffe1000 and writes it there too. `__wine_unixlib_handle` gets the host address of `unix_call_funcs`, an opaque handle. M3 writes the dispatcher addresses.
- **`BOOT_STOP_AT_ENTRY`:** `signal_start_thread` builds the start state as `init_syscall_frame` does (`signal_x86_64.c` L2896):
  - a `CONTEXT` at `((StackBase − 0x28) & ~15) − sizeof(CONTEXT)` with `ContextFlags = CONTEXT_FULL`, Rip = `RtlUserThreadStart`, Rcx = the entry, Rdx = the PEB, Rsp = StackBase − 0x28, SegCs 0x33, SegDs, SegEs, SegGs and SegSs 0x2b, SegFs 0, EFlags 0x200, the FPU control word 0x27f and MXCSR 0x1f80;
  - the main thread's state block: RIP = `LdrInitializeThunk`, RCX = the `CONTEXT`, RDX = the PEB, RSP = the `CONTEXT` − 8, the other GPRs 0, RFLAGS 0x200, MXCSR 0x1f80, FCW 0x27f, GS base = the TEB;

  then it `longjmp`s back to `boot`, which returns 0. `tw_main_state()` gives the state block's address.
- **MEMFS gets the boot set** from the JS host before `boot`:
  - the prefix's `.reg` files, the `dosdevices` symlinks and `drive_c`'s directories;
  - the PE files the boot opens, the NLS files and `wine.inf` (`closure.json`'s `data_files`);
  - `C:\tempwind\hello.exe` (`tests/native`'s hello).

  The boot test records the files the boot opened. Loading file contents on demand is M3.

## 9. Blocking and threads (M2: one thread)
- **`green.c`:**
  - `green_block` is the only switch point. Around it, C saves and restores the spike's save set (`abi.md` v5, "Green threads"); `depth` joins the set in M3, once translated code runs.
  - It provides sleeping until a deadline, yielding, and a wake queue.
  - Wine's blocking libc calls are routed there: `select` and `usleep` sleeps, `sched_yield`, `poll` on the server's pipes and the waits of section 7. A blocking call that green.c doesn't handle stops loudly.
- **`green_pthread.c`**, the single-thread part of the green pthread layer. The `-ww` libc that `-sSHARED_MEMORY` links without `-pthread` has no pthread functions at all (`research.md`, 2026-11-13), so this is needed from the first link:
  - mutexes (recursive ones included), condition variables, `pthread_once`, keys, `pthread_self`, `pthread_sigmask` and the attribute functions;
  - keys are per green thread. `NtCurrentTeb()` (`thread.c`) reads `teb_key`, so it follows the running green thread;
  - a thread that suspends while it holds a mutex is a bug, and the layer asserts on it;
  - a condition wait goes through `green.c` (a wait that nothing can end is the scheduler's deadlock);
  - `pthread_create` stops loudly until M4.
- **The JS scheduler** (`runtime/src/wine/`): when no green thread is runnable, it calls `tw_next_timeout()`, then `setTimeout` for that long, then `tw_run_timeouts()`, and resumes the woken threads.
  - `tw_next_timeout` counts thread waits and timers only. It ignores the server's KUSER tick (16 ms, `server/fd.c` L898) and its 30 s registry save.
  - Nothing runnable and no timeout is a deadlock: the scheduler stops loudly with each thread's wait.

## 10. Tests
- **C harnesses:** `native/wine/tests/NAME.c` defines `int tw_test_main(void)`, entered through `promising` by the JS host. It reports through `native/wine/tests/harness.h`: one line per check on stdout, `ok NAME` or `not ok NAME: detail`, and a last line `done PASSED/TOTAL`.
- **Node tests:** `tests/wine/NAME.test.mjs` runs `test-NAME` and asserts that there is no `not ok` line and that the checks that ran are the expected list, by name. `npm run test:wine` runs `tests/wine/*.test.mjs` against `target/wine-unix` (or `TW_WINE_UNIX_DIR`).
- **A check that expects a loud stop** runs alone in a fresh instance: the Node test sets `TW_TEST_ONLY=<check>` in `ENV`, the harness runs only that check, and the test asserts that the run ended with the expected `tempwind:` line on stderr (or the scheduler's deadlock error) and not with `done`.
- **`tests/wine/prepare.sh`** fetches the `wine.lock` assets into `target/wine`, builds `hello.exe` and `kuser-dump.exe`, runs `kuser-dump.exe` under native Wine 11 (with `TZ=UTC`) to write `target/wine/kuser.bin`, and builds the Unix side, or fetches `wine-unix.lock`'s release with `--fetch`.
- **The M2 checks:**
  - `link`: the module compiles and instantiates in Node with the 4 GiB memory; its imports are a subset of `imports.txt`; a raw export runs (`malloc` and `free`).
  - `virtual`, which needs no server: reserve, commit, protect, free and query; zero on recommit; write-watch and `PAGE_WATCH`; allocations stay in the guest regions; the heap cap of section 5; file views through the backend's own functions, with write-back and the second writable view stopping; the KUSER page; pointer validation.
  - `wait`, on one thread: an event wait with a timeout returns `STATUS_TIMEOUT` after at least that time; a signaled event returns at once; a timer fires; a zero timeout polls; `NtDelayExecution` both alertable and not; a wait nothing can end stops loudly.
  - `section`: image placement through `NtCreateSection` and `NtMapViewOfSection`, at the preferred base and in a `ranges64` slot when the base is taken; a writable shared file view written back through the server.
  - `boot`:
    - RIP = `LdrInitializeThunk`, from the test's own read of ntdll's export table in memory;
    - the `CONTEXT`'s fields and the state block of section 8, with GS base = the TEB;
    - ntdll and hello.exe as `MEM_IMAGE` at their preferred bases;
    - `PEB->ApiSetMap` inside apisetschema's view;
    - prefix and overlay values read through `NtQueryValueKey`;
    - NLS loaded;
    - KUSER equal to `kuser.bin`, except the fields Wine fills from the clock and those that come from the CPU profile (the test lists them, naming this section);
    - the list of files the boot opened.

## Risks
- **The first full link** may need many stubs and renames. WP1 reports at its first full link, before the gates are clean.
- **Emscripten's pipes are unbounded in 6.0.12.** 7.0.0 caps them at 64 KiB; the server's partial-write path for a larger reply would then need `main_loop`. We stay on 6.0.12 (`research.md`).
- **A 4 GiB initial memory** must be cheap to create in Node and in a Chromium Worker (pages reserved, not committed). WP0 measures it.
